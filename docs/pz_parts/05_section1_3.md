## 1.3 Проектирование

### 1.3.1 Логическое обоснование и описание структуры и алгоритмов функционирования программы

#### 1.3.1.1 Выбор архитектурного паттерна

На этапе проектирования рассматривались три подхода к организации веб-приложения: традиционное серверное рендеринг (SSR, Server-Side Rendering), многостраничное приложение с динамическими элементами (MPA + AJAX) и одностраничное приложение (SPA) с отдельным REST API.

Подход SSR предполагает, что сервер при каждом запросе формирует готовую HTML-страницу. Достоинства — хорошая индексируемость поисковыми роботами и быстрое отображение первого экрана. Недостатки применительно к данному проекту — высокая нагрузка на сервер при работе производственной панели, где частые обновления данных потребовали бы постоянной перезагрузки страниц.

Подход MPA + AJAX улучшает отзывчивость интерфейса, сохраняя серверный рендеринг для начальной загрузки. Однако при реализации сложных интерактивных компонентов (канбан-доска, матрица допусков, лайтбокс галереи) этот подход быстро усложняется и превращается в де-факто SPA на уровне отдельных страниц.

Подход SPA + REST API выбран как оптимальный по следующим основаниям:

1) Чёткое разделение ответственности: бэкенд отвечает исключительно за данные и бизнес-логику, фронтенд — за представление. Это позволяет разрабатывать и тестировать их независимо;
2) Интерфейс остаётся отзывчивым при навигации: переход между каталогом, карточкой товара и производственной панелью происходит без перезагрузки страницы;
3) REST API, разработанный для фронтенда, автоматически становится интерфейсом для возможных будущих клиентов — мобильного приложения, сторонних интеграций;
4) SEO-индексируемость для данного проекта менее критична: клиенты приходят преимущественно из группы ВКонтакте, а не через поисковые системы.

#### 1.3.1.2 Общая архитектура системы

Система построена по классической трёхзвенной клиент-серверной архитектуре с дополнительным уровнем обратного прокси.

[Рисунок 2 — Архитектурная схема системы (C4 Level 2)]

Описание уровней системы:

**Клиентский уровень.** React SPA, собранный инструментом Vite в набор статических файлов (HTML, JavaScript, CSS). При первом обращении браузер получает index.html и JavaScript-бандл; в дальнейшем все взаимодействия с сервером выполняются через fetch-запросы к REST API. Состояние приложения хранится в памяти браузера (React-состояние корневого компонента App).

**Уровень обратного прокси (Nginx).** Принимает все входящие HTTP-соединения на порту 8080. Для URL-путей, начинающихся с /api/ или /admin/, проксирует запросы на Gunicorn через UNIX-сокет. Для остальных путей возвращает статические файлы из директории dist/ (собранный фронтенд); для любого неизвестного пути возвращает index.html, обеспечивая SPA-роутинг.

**Уровень приложения (Gunicorn + Django).** Gunicorn — WSGI-сервер, который запускает несколько рабочих процессов Django. Django обрабатывает запросы, применяет бизнес-логику, взаимодействует с базой данных через ORM и возвращает JSON-ответы.

**Уровень данных.** SQLite — встроенная в Python база данных без отдельного процесса. Файл базы хранится на диске сервера в директории проекта. Для продакшн-развёртывания с высокой нагрузкой возможна миграция на PostgreSQL без изменений в коде (только настройки Django).

#### 1.3.1.3 Алгоритм инициализации приложения

При открытии сайта браузер загружает статические файлы фронтенда, после чего React-приложение выполняет три параллельных HTTP-запроса:

1) GET /api/csrf/ — получение CSRF-cookie. Django устанавливает cookie csrftoken, которая в дальнейшем используется для всех небезопасных запросов;
2) GET /api/bootstrap/ — основной запрос инициализации. Возвращает в одном ответе: массив всех товаров (до 1000 позиций), массив отзывов, объект с внешними ссылками (ВКонтакте, Telegram). Этот подход устраняет необходимость нескольких последовательных запросов и ускоряет первый рендер каталога;
3) GET /api/auth/me/ — проверка текущей сессии. Если пользователь уже был авторизован (cookie sessionid сохранился с предыдущего сеанса), возвращает данные пользователя; в противном случае возвращает 401, и кнопка «Войти» остаётся видимой.

После получения ответа от /api/bootstrap/ каталог отображается немедленно. Фильтрация, поиск и сортировка выполняются на стороне клиента через useMemo, без дополнительных запросов к серверу.

#### 1.3.1.4 Алгоритм создания заказа и автоматической генерации задач

Создание заказа — ключевой производственный сценарий системы. Алгоритм реализован в представлении WorkshopOrderCreateView и вспомогательной функции _create_tasks_for_order:

1) Руководитель заполняет форму заказа: выбирает или создаёт клиента, указывает тип заказа (предмет/комплект/услуга), выбирает конкретное изделие или комплект, задаёт дедлайн, при необходимости — сумму и аванс;
2) Если сумма не указана явно, она берётся из поля price_from изделия или комплекта; аванс по умолчанию устанавливается в 50% от суммы;
3) В БД создаётся запись Order с начальным статусом new;
4) Вызывается _create_tasks_for_order(order). Функция анализирует тип заказа:
   - Если тип «предмет» — создаётся одна задача Task с product=изделие, status=pending;
   - Если тип «комплект» — для каждого изделия в составе комплекта создаётся отдельная задача Task;
   - Если тип «услуга» — создаётся одна задача с product=None и product_name из поля конфигурации;
5) Созданные задачи автоматически становятся видимыми в стеке тем мастерам, у которых есть допуск к соответствующему изделию.

[Рисунок 3 — Диаграмма деятельности: алгоритм создания заказа и задач]

Такая схема обеспечивает автоматический маршрутинг работ без ручного назначения: руководитель создаёт заказ, задачи попадают в общий пул, из которого мастера самостоятельно берут работу в соответствии со своими допусками.

#### 1.3.1.5 Алгоритм системы допусков мастеров

Матрица допусков реализуется через модель MasterApproval, каждая запись которой связывает одного мастера (ссылка на User) с одним изделием (ссылка на Product). Уникальное ограничение по паре (master, product) исключает дублирование.

При запросе стека задач (GET /api/workshop/tasks/?view=stack) система:
1) Получает список product_id из таблицы MasterApproval, отфильтрованный по текущему пользователю;
2) Возвращает только те задачи, у которых product_id входит в этот список;
3) Дополнительно фильтрует задачи по статусу pending (только те, которые никем не взяты).

Суперадмин (is_superuser) получает все задачи вне зависимости от допусков, что позволяет руководителю контролировать весь производственный стек.

Жизненный цикл задачи имеет три статуса: pending → taken → done. Обратный переход (taken → pending) возможен при освобождении задачи мастером. Переход done → pending не предусмотрен; если работа должна быть переделана, создаётся новая задача.

#### 1.3.1.6 Алгоритм репоста ВКонтакте → Telegram

Интеграция реализует автоматическую пересылку публикаций группы ВКонтакте в Telegram-канал. Алгоритм:

1) В настройках группы ВКонтакте (раздел «Работа с API» → «Callback API») настраивается сервер с URL /api/integrations/vk/callback/ и секретным ключом;
2) При публикации нового поста ВКонтакте отправляет POST-запрос на указанный URL;
3) Обработчик VkCallbackView проверяет секретный ключ в теле запроса. Несовпадение ключа — ответ 403, обработка прерывается;
4) Проверяется тип события: если type ≠ wall_post_new, возвращается «ok» без обработки;
5) Если поле copy_history присутствует в объекте поста — это репост чужой записи; пропускается;
6) Если post_type = «postpone» — запись ещё не опубликована фактически; пропускается;
7) Дедупликация: проверяется кэш Django по ключу vk_post_{owner_id}_{post_id} с TTL 24 часа. Если ключ присутствует — дубль, пропускается. Иначе ключ устанавливается;
8) Пост сохраняется в модель VKPost (для отображения в блоке новостей на сайте);
9) Функция parse_post() извлекает текст и фотографии. Текст очищается от VK-тегов (упоминания вида [id123|Имя] преобразуются в «Имя»), к тексту добавляется постоянная ссылка на запись. Текст усекается до лимита Telegram (1024 символа для подписи к фото, 4096 для текстового сообщения);
10) Функция repost_to_channel() отправляет пост в Telegram: одно фото — sendPhoto с подписью; несколько фото — sendMediaGroup (альбом до 10 фото); только текст — sendMessage;
11) Telegram-бот отвечает 200 OK. ВКонтакте получает ответ «ok» в любом случае — ошибки в интеграции с Telegram не влияют на обработку события ВКонтакте.

#### 1.3.2.2 Взаимодействие с ВКонтакте

Взаимодействие с платформой ВКонтакте организовано через Callback API — механизм, при котором платформа активно уведомляет приложение о событиях, отправляя POST-запросы. Это исключает необходимость периодических опросов (polling) со стороны приложения.

Для активации Callback API в настройках сообщества ВКонтакте выполняется одноразовая процедура подтверждения: ВКонтакте отправляет запрос с типом confirmation на настроенный URL; сервер возвращает строку подтверждения (VK_CONFIRMATION_TOKEN), доказывая, что данный URL принадлежит администратору сообщества.

Получаемые события: wall_post_new (новая запись на стене). Сервер подписывается именно на этот тип событий в настройках Callback API.

Дополнительный канал взаимодействия с ВКонтакте — RSS-лента группы (https://vk.com/rss/wall-{owner_id}.rss). Этот механизм используется в эндпоинте /api/vk-posts/ для получения актуальных публикаций без API-ключа, только по открытому идентификатору сообщества.

#### 1.3.2.3 Взаимодействие с Telegram

Отправка сообщений в Telegram реализуется через Telegram Bot API. Приложение выступает в роли активного клиента (не вебхук-получателя): при получении события от ВКонтакте сервер сам инициирует HTTP-запрос к API Telegram.

Используемые методы Bot API:
- sendMessage — отправка текстового сообщения в канал (параметры: chat_id, text);
- sendPhoto — отправка одной фотографии с подписью (параметры: chat_id, photo, caption);
- sendMediaGroup — отправка группы фотографий (альбом) с подписью на первом элементе (параметры: chat_id, media — массив объектов InputMedia).

Выбор метода осуществляется автоматически функцией repost_to_channel() в зависимости от наличия и количества фотографий в исходном посте. Все три метода задействуют единый токен Telegram-бота, настроенный в переменной окружения TELEGRAM_BOT_TOKEN.

#### 1.3.2.4 Взаимодействие с SMTP-сервером

Email-уведомления о приближающихся дедлайнах отправляются через Django-модуль django.core.mail. Параметры SMTP-подключения (хост, порт, логин, пароль) передаются через переменные окружения. Поддерживаются как SSL-соединение (порт 465), так и TLS через STARTTLS (порт 587).

Management-команда notify_urgent_orders запускается планировщиком cron раз в сутки в 09:00. Она находит все активные заказы (статус new или in_progress) с дедлайном через 14, 7 или 3 дня от текущей даты и отправляет письма ответственному мастеру и администратору.

#### 1.3.3.2 Входные данные системы

Система принимает входные данные из трёх источников.

**HTTP-запросы от браузера.** Тело запроса передаётся в формате JSON (Content-Type: application/json). Параметры фильтрации и пагинации передаются в строке запроса (query string). Файлы (изображения) в данной версии системы не загружаются через API — используются ссылки на внешние URL.

**Вебхук-событие от ВКонтакте.** POST-запрос на /api/integrations/vk/callback/ с телом в формате JSON по спецификации VK Callback API. Ключевые поля события wall_post_new: type (тип события), object.id (ID поста), object.owner_id (ID сообщества), object.text (текст записи), object.attachments (вложения: фотографии, ссылки), object.date (Unix timestamp публикации), secret (секретный ключ).

**Вебхук-событие от Telegram.** POST-запрос на /api/integrations/telegram/webhook/ с телом по спецификации Telegram Bot API (объект Update). В текущей версии принимается и подтверждается, но содержательная обработка не реализована (заглушка для будущего расширения).

#### 1.3.3.3 Выходные данные системы

**Ответы REST API** возвращаются в формате JSON с кодом состояния HTTP, соответствующим результату операции (200 OK, 201 Created, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found).

Ответ /api/bootstrap/ содержит:
- products — массив объектов Product, сериализованных в camelCase (priceFrom, leadTime, protectionClass). Поле setDiscounts содержит список комплектов, в которые входит товар, с процентом скидки;
- reviews — массив объектов Review;
- links — объект с ключами vkCommunity, vkMessages, telegramPublic;
- total, page, hasNext — метаданные пагинации.

**Ответ на вебхук ВКонтакте** — строка «ok» с Content-Type: text/plain. Требование задокументировано в документации ВКонтакте Callback API: любой ответ, отличный от «ok», интерпретируется как ошибка, и ВКонтакте повторяет попытку отправки.

**Статические файлы** (HTML, CSS, JavaScript, изображения) раздаются Nginx из директории dist/ при запросах к публичной части сайта.

#### 1.3.3.4 Сериализация данных

DRF-сериализаторы преобразуют объекты Django-моделей в JSON и обратно. В ProductSerializer применено ручное сопоставление полей: snake_case-поля модели (price_from, lead_time, protection_class) преобразуются в camelCase (priceFrom, leadTime, protectionClass) для удобства использования в JavaScript/TypeScript-коде фронтенда.

Вычисляемое поле setDiscounts не хранится в базе данных: оно вычисляется в момент сериализации через SerializerMethodField. Для каждого товара выполняется запрос к ProductSet, отфильтрованный по включению данного товара, и вычисляется процент скидки как (1 — price_from_комплекта / sum(price_from_товаров)) × 100.

Для оптимизации производительности все связанные объекты загружаются в один запрос через prefetch_related. Без этой оптимизации при 200 товарах в каталоге возникла бы проблема N+1 запросов.
