# Раздел 2 Практическая часть работы

## 2.1 Программная реализация

### 2.1.1 Технические средства реализации

#### 2.1.1.1 Серверная часть

Серверная часть системы реализована на языке **Python 3.11** с использованием веб-фреймворка **Django 5.2**.

Django выбран по нескольким ключевым соображениям. Во-первых, фреймворк предоставляет встроенную систему аутентификации и управления сессиями, которая удовлетворяет всем требованиям безопасности без необходимости реализовывать её самостоятельно. Во-вторых, механизм миграций базы данных обеспечивает управляемую эволюцию схемы при итеративной разработке. В-третьих, встроенная панель администратора Django (/admin/) предоставляет резервный интерфейс управления данными без дополнительных усилий. Версия 5.2 выбрана как актуальная LTS-версия на момент начала разработки, гарантирующая поддержку до 2028 года.

Для построения REST API использован **Django REST Framework 3.16** (DRF). Он предоставляет базовые классы APIView с автоматической сериализацией/десериализацией JSON, встроенным CSRF-контролем и механизмом разрешений. Архитектура «представление на основе классов» (class-based views) позволила вынести общую логику проверки аутентификации в базовый класс и переопределять её только там, где это необходимо (публичные эндпоинты, webhook-приёмники).

Для раздачи статических файлов применена библиотека **WhiteNoise 6.9** с расширением Brotli. WhiteNoise интегрируется в цепочку WSGI-middleware и позволяет Django самостоятельно обслуживать статические файлы с высоким уровнем производительности: файлы кешируются в памяти при старте, заголовки Cache-Control устанавливаются автоматически, компрессия Brotli снижает объём передаваемых данных на 15–25% по сравнению с gzip.

Настройка доступа с фронтенда (другой порт в режиме разработки) обеспечена библиотекой **django-cors-headers 4.7**. CORS-заголовки добавляются только для перечисленных в настройках доменов, что исключает несанкционированные кросс-доменные запросы.

Для планирования фоновых задач — в частности, email-уведомлений о приближающихся дедлайнах — применена библиотека **python-crontab 3.3**, позволяющая программно управлять crontab-записями текущего пользователя из кода Django-команды управления.

HTTP-запросы к внешним API (ВКонтакте, Telegram) выполняются через библиотеку **requests 2.32**.

Производственный WSGI-сервер — **Gunicorn**, запускающий три рабочих процесса. Gunicorn принимает соединения через UNIX-сокет `/run/calradia/calradia.sock`, что обеспечивает более низкую латентность по сравнению с TCP-соединениями на localhost и исключает лишние сетевые затраты.

Управление жизненным циклом сервиса осуществляется через **systemd**. Unit-файл calradia.service задаёт параметры RuntimeDirectory (автоматическое создание директории сокета при старте), EnvironmentFile (загрузка секретов из .env) и перезапуск при сбое (Restart=on-failure). Это обеспечивает требование доступности системы не менее 99,5%.

В качестве **СУБД** используется SQLite 3. Файл базы данных хранится в корневой директории проекта. Выбор SQLite обоснован малым объёмом данных (менее 1000 изделий, менее 50 одновременных заказов) и отсутствием необходимости в параллельных операциях записи. SQLite не требует отдельного серверного процесса, что упрощает развёртывание на одном VPS.

Обратный прокси-сервер **Nginx** принимает запросы на порту 8080 и распределяет их: запросы к `/api/*` и `/admin/*` передаются Gunicorn через UNIX-сокет, остальные — обслуживаются из директории с собранным фронтендом. Конфигурация `try_files $uri $uri/ /index.html` обеспечивает SPA-роутинг: обновление страницы на любом URL возвращает index.html, после чего маршрутизация выполняется React Router на стороне клиента.

#### 2.1.1.2 Клиентская часть

Клиентская часть разработана как одностраничное приложение (SPA) на языке **TypeScript 5.x** с использованием библиотеки **React 19**.

React 19 выбран в первую очередь ради компонентной модели, позволяющей разбить сложный интерфейс (каталог с фильтрами, канбан-доска, матрица допусков, галерея с лайтбоксом) на независимые переиспользуемые компоненты. Хуки состояния и эффектов (useState, useEffect, useMemo) обеспечивают реактивный интерфейс без дополнительных библиотек управления состоянием — объём данных приложения достаточно мал, чтобы хранить их в родительском компоненте App и передавать через props.

TypeScript обеспечивает статическую типизацию: все доменные сущности (Product, Order, Task, Client, MasterApproval и другие) описаны в файле types.ts, что позволяет компилятору обнаруживать несоответствия типов на этапе разработки.

Сборщик **Vite 6** обеспечивает быстрый цикл разработки (HMR — горячая замена модулей) и оптимизированную финальную сборку (разбиение на чанки, tree-shaking, минификация). Время первоначальной сборки не превышает 15 секунд на машине разработчика.

Для иконографии применена библиотека **Lucide React** — набор из более 1000 SVG-иконок с консистентным визуальным стилем, поставляемых как React-компоненты и включаемых только в той части, что используется в коде (tree-shakeable).

Сторонние CSS-фреймворки не используются: все стили написаны вручную в файле styles.css с использованием CSS-переменных (custom properties) для цветовой палитры и интервалов. Это обеспечивает полный контроль над визуальным стилем в соответствии с тематикой средневековой кузницы.

Для автоматического тестирования фронтенда применён фреймворк **Vitest** совместно с **@testing-library/react**. Vitest интегрируется с Vite и позволяет использовать ту же конфигурацию TypeScript, что и в основном коде приложения. Покрытие кода измеряется через **@vitest/coverage-v8**.

#### 2.1.1.3 Инфраструктура и окружение разработки

Развёртывание производится на VPS под управлением **Debian 11** с 2 ГБ оперативной памяти и 1 vCPU. Такая конфигурация типична для малого бизнеса и соответствует требованиям нефункциональной спецификации.

Управление зависимостями серверной части осуществляется через стандартный файл `requirements.txt`. Для изоляции зависимостей применяется виртуальное окружение Python (venv). Зависимости клиентской части управляются через **npm** и зафиксированы в `package-lock.json`.

Конфигурационные секреты (SECRET_KEY, ключи VK и Telegram, SMTP-реквизиты) хранятся в файле `.env` на сервере и загружаются в окружение процесса Django через директиву `EnvironmentFile` systemd-юнита. Файл `.env.example` с описанием всех параметров включён в репозиторий.

Система контроля версий — **Git**, удалённый репозиторий размещён на GitHub. Ветвление организовано по модели feature-branches.

### 2.1.2 Описание разработанных алгоритмов

#### 2.1.2.1 Алгоритм начальной загрузки данных (bootstrap)

Производительность первого рендера каталога является критическим показателем пользовательского опыта. Если бы фронтенд загружал товары, отзывы и ссылки тремя отдельными запросами, задержка вырастала бы втрое из-за последовательного выполнения fetch-вызовов (каждый последующий ожидает предыдущего).

Эндпоинт `/api/bootstrap/` решает эту проблему, объединяя все необходимые данные в одном ответе. Алгоритм работы представления BootstrapView:

1. Формируется QuerySet товаров с предварительной загрузкой (prefetch_related) связанных фотографий галереи и комплектов. Это исключает проблему N+1 запросов: вместо одного SQL-запроса на каждый из N товаров выполняется один общий запрос на все фотографии.
2. Все товары сериализуются в JSON-массив. Клиент получает полный каталог и хранит его в памяти; вся последующая фильтрация и поиск выполняются клиентским кодом через useMemo без обращения к серверу.
3. Запрашиваются последние 10 опубликованных отзывов — объём достаточный для отображения на странице отзывов.
4. Из таблицы IntegrationLink извлекаются внешние ссылки (ВКонтакте, Telegram, электронная почта). Если записи в базе отсутствуют, используются значения из settings.py.
5. Все три объекта объединяются в один словарь и возвращаются с кодом HTTP 200.

Эндпоинт открыт для анонимного доступа (permission_classes не заданы), поскольку содержит только публичные данные.

#### 2.1.2.2 Алгоритм создания заказа и автоматической генерации задач

Приём нового заказа — наиболее сложный бизнес-сценарий системы. Представление WorkshopOrderCreateView реализует транзакционный алгоритм, состоящий из четырёх фаз:

**Фаза 1. Валидация входных данных.** Из тела запроса извлекаются: имя клиента (обязательное поле), тип заказа (Одиночный/Комплект), список идентификаторов товаров, дата дедлайна (строка ISO 8601), общая сумма и аванс (числа). Отсутствие обязательного поля возвращает HTTP 400 с описанием ошибки.

**Фаза 2. Создание или поиск клиента.** По имени ищется существующий клиент (поиск без учёта регистра). Если клиент не найден — создаётся новая запись. Это позволяет руководителю быстро оформлять повторные заказы, вводя только имя.

**Фаза 3. Создание заказа.** Запись Order сохраняется в базе с начальным статусом «Новый» (new), привязкой к клиенту, датой дедлайна и финансовыми параметрами. К заказу привязываются выбранные товары через отношение ManyToMany.

**Фаза 4. Автоматическая генерация задач.** Вызывается вспомогательная функция `_create_tasks_for_order(order)`. Алгоритм функции:
- Для каждого товара из состава заказа определяется его категория (category): helmet, armour, chainmail, leather, bracers и другие.
- Категория маппируется на направление специализации (Direction) через словарь соответствия: например, категория chainmail → направление chain_mail; категория leather → направление leather.
- По каждому направлению создаётся одна запись Task со статусом «В стеке» (stack), привязкой к заказу и текстовым описанием на основе названия товара.
- Дубликаты задач одного направления в рамках одного заказа не создаются: если заказ содержит несколько кольчужных элементов, создаётся одна задача для мастера по кольчуге.

После сохранения всех задач метод `_sync_order_status(order)` пересчитывает статус заказа в зависимости от статусов задач: если все задачи выполнены — заказ переходит в «Готов»; если хотя бы одна в работе — «В производстве»; если ни одна не взята — «Новый».

#### 2.1.2.3 Алгоритм проверки допуска мастера

Матрица допусков определяет, к задачам каких направлений имеет доступ конкретный мастер. Алгоритм реализован в методе PATCH представления WorkshopTaskDetailView и включает следующие проверки:

1. **Проверка авторизации.** Неавторизованный запрос немедленно отклоняется (HTTP 401).
2. **Получение задачи.** Задача ищется по идентификатору. Если не найдена — HTTP 404.
3. **Ветвление по действию.** В зависимости от переданного поля action выполняется одна из трёх ветвей: take (взять в работу), release (вернуть в стек), done (отметить выполненной).
4. **Проверка допуска при взятии задачи.** Для пользователей без флага is_superuser выполняется дополнительная проверка: существует ли запись MasterApproval с сочетанием (мастер = текущий пользователь, направление = направление задачи). Если запись отсутствует — HTTP 403 с сообщением «Нет допуска к задачам этого направления».
5. **Проверка статуса задачи.** Задачу можно взять только из состояния «В стеке»; вернуть или отметить выполненной — только из состояния «В работе». Нарушение — HTTP 400.
6. **Проверка «чужой задачи».** Вернуть задачу или отметить её выполненной может только тот мастер, который её взял, либо администратор. Иначе — HTTP 403.

Суперпользователь проходит проверки с пункта 4 по 6 в упрощённом режиме: допуск не требуется, «чужая задача» не является ограничением.

Аналогичная логика применяется к стеку задач, видимому мастеру в WorkshopTasksView: запрос к GET /api/workshop/tasks/ для мастера (не суперпользователя) возвращает только задачи со статусом «В стеке» по направлениям, на которые у него есть допуск, плюс задачи, уже взятые им самим.

#### 2.1.2.4 Алгоритм репоста публикации ВКонтакте в Telegram

Интеграция ВКонтакте → Telegram реализована по событийной модели: ВКонтакте отправляет HTTP-запрос на сервер при каждом новом событии в группе.

**Шаг 1. Получение события.** Nginx проксирует POST-запрос на `/api/vk/callback/` к представлению VkCallbackView. Представление проверяет HMAC-подпись запроса (поле secret должно совпадать с токеном из settings.py). Запросы с неверной подписью отклоняются (HTTP 403).

**Шаг 2. Обработка подтверждения.** При первой настройке Callback API ВКонтакте отправляет событие с type=confirmation. Представление возвращает строку подтверждения в формате plaintext — это необходимо для верификации адреса callback.

**Шаг 3. Парсинг поста.** При получении события типа wall_post_new вызывается функция `parse_post(post_data)` из модуля services/vk.py. Функция:
- Извлекает текст поста, обрезает упоминания (@club...) через регулярное выражение.
- Ограничивает длину текста 1000 символами.
- Собирает список URL фотографий: для каждого вложения типа photo выбирается версия с наибольшим разрешением.
- Фильтрует рекламные посты (наличие поля marked_as_ads == 1).

**Шаг 4. Проверка дедупликации.** По идентификатору поста ВКонтакте (vk_id) проверяется наличие записи в таблице VKPost. Если запись существует — пост уже был переслан, обработка завершается. Иначе запись создаётся.

**Шаг 5. Отправка в Telegram.** Вызывается функция `repost_to_telegram(text, photos)` из модуля services/telegram.py. Если список фотографий пуст — отправляется простое текстовое сообщение (sendMessage). При наличии одной фотографии — sendPhoto с подписью. При наличии нескольких — sendMediaGroup (альбом).

**Шаг 6. Обработка ошибок.** Если Telegram API недоступен (сеть, превышение лимита запросов), исключение перехватывается, в лог записывается предупреждение, а в ВКонтакте всё равно возвращается HTTP 200 с телом `ok`. Это обязательно: если Callback API ВКонтакте получает ошибку, он повторяет запрос несколько раз, что приведёт к дублированию постов.

#### 2.1.2.5 Алгоритм email-уведомлений о дедлайнах

Уведомления отправляются управляющей командой Django `notify_urgent_orders`. Алгоритм:

1. Запрашиваются все заказы в статусах «Новый», «В производстве» и «Готов» (кроме «Отменён» и «Выдан»).
2. Для каждого заказа вычисляется количество дней до дедлайна: `days_left = (deadline - today).days`.
3. Если days_left равно 14, 7 или 3 — формируется email-уведомление руководителю с именем клиента, описанием заказа и датой дедлайна.
4. При наличии флага `--dry-run` команда только выводит список заказов, которые попали бы в рассылку, без фактической отправки.
5. Команда добавляется в crontab операционной системы: задание выполняется ежедневно в 09:00 по серверному времени.

#### 2.1.2.6 Клиентская фильтрация каталога

Каталог, полученный от `/api/bootstrap/`, хранится в состоянии React-компонента App. Параметры активных фильтров (категория, период, материал, размер, статус наличия, строка поиска, порядок сортировки) также хранятся в состоянии App.

Вычисление отфильтрованного массива товаров для отображения реализовано через хук `useMemo`, зависящий от массива товаров и текущих параметров фильтрации. При изменении любого параметра хук пересчитывается без обращения к серверу.

Алгоритм фильтрации применяет условия последовательно: сначала фильтр по категории, затем по периоду, материалу, размеру, статусу. Строка поиска сопоставляется с полями name и subtitle через `toLowerCase().includes()`. Сортировка применяется в последнюю очередь через `Array.prototype.sort()` с компаратором, соответствующим выбранному критерию (по умолчанию, по дате добавления, по популярности, по сроку изготовления).

### 2.1.3 Описание интерфейса пользователя

#### 2.1.3.1 Публичная часть: каталог

Главная страница (`/`) представляет каталог изделий. Страница делится на две функциональные зоны: панель фильтров слева и сетка карточек товаров справа.

Панель фильтров (компонент FiltersPanel) содержит группы фильтров: тип изделия (категория), исторический период, материал, размеры, наличие. В верхней части панели расположена строка поиска с немедленной реакцией на ввод (без задержки debounce, поскольку фильтрация выполняется локально). Кнопка «Сбросить фильтры» появляется только при наличии активных условий.

Сетка карточек (компонент ProductCard) отображается в три колонки на широких экранах и в одну — на мобильных. Каждая карточка содержит: фотографию (первое фото из галереи), название, исторический период, краткий подзаголовок, стоимость и индикатор наличия. Карточки товаров, входящих в какой-либо комплект, отображают значок скидки с процентом. При клике на карточку открывается страница детальной карточки.

Управление сортировкой реализовано компонентом SortControl — выпадающий список с вариантами «По умолчанию», «Сначала новые», «По популярности», «По сроку изготовления».

#### 2.1.3.2 Детальная карточка изделия

Детальная карточка (`/catalog/:slug`) открывается при клике на карточку в каталоге. Страница содержит:

- **Фотогалерею** с возможностью смены основного фото кликом на миниатюру. При клике на основное фото открывается лайтбокс — полноэкранный просмотр с кнопками навигации по снимкам и закрытием клавишей Escape.
- **Технические характеристики** в структурированном виде: материал, сталь, класс защиты, доступные размеры, срок изготовления, вес.
- **Историческую справку** — текстовый блок с описанием исторического прообраза изделия.
- **Блок «Заказать»** — краткий призыв к действию со ссылкой на мессенджер мастерской.
- **Информацию о комплектах**, в состав которых входит изделие: если товар является частью одного или нескольких комплектов, отображаются карточки этих комплектов с указанием скидки.

#### 2.1.3.3 Страница комплектов

Страница комплектов (`/sets`) отображает список тематических наборов изделий. Каждый комплект представлен карточкой с названием, описанием исторического периода, изображением и двумя ценами: суммарной ценой без скидки (зачёркнутой) и ценой комплекта (с применением скидки).

При переходе на страницу комплекта (`/sets/:slug`) отображается детальный состав: список входящих изделий с фотографиями, индивидуальными ценами и ссылками на полные карточки. Итоговая цена комплекта со скидкой выделяется.

#### 2.1.3.4 Страница отзывов

Страница отзывов (`/reviews`) отображает список отзывов клиентов в обратном хронологическом порядке. Каждый отзыв содержит имя автора, дату, рейтинг (от 1 до 5 звёзд) и текст.

Форма добавления отзыва расположена внизу страницы. Форма доступна без авторизации. Поля: имя, рейтинг, текст отзыва. После отправки форма очищается, новый отзыв добавляется в список без перезагрузки страницы.

#### 2.1.3.5 Страница входа

Страница авторизации (`/login`) содержит минималистичную форму с полями «Логин» и «Пароль» и кнопкой «Войти». При успешной авторизации выполняется редирект на производственную панель. При ошибке отображается сообщение об ошибке непосредственно в форме.

Форма отправляет POST-запрос на `/api/auth/login/` с CSRF-токеном, полученным ранее при загрузке приложения. Django устанавливает sessionid-cookie, которая сохраняется браузером и используется при всех последующих запросах.

#### 2.1.3.6 Производственная панель: сводка

После авторизации пользователь попадает на сводную страницу производственной панели (`/workshop`). Сводка (компонент WorkshopPanel, вкладка «Сводка») отображает:

- **Счётчики заказов по статусам**: карточки «Новые», «В производстве», «Готовы к выдаче», «Выдано», «Отменено» с числом заказов в каждом статусе.
- **Список горящих заказов**: заказы с дедлайном в ближайшие 14 дней, отсортированные по близости дедлайна. Для каждого заказа отображаются: имя клиента, тип заказа, дедлайн и оставшееся число дней. Строки с дедлайном менее чем через 7 дней выделены предупредительным цветом.
- **Мои задачи в работе**: задачи, взятые текущим мастером, с возможностью отметить выполненной непосредственно со сводки.

#### 2.1.3.7 Производственная панель: канбан-доска заказов

Вкладка «Заказы» отображает канбан-доску с колонками по статусам. Каждая карточка заказа содержит: имя клиента, тип, список изделий, дедлайн, аванс и финальная сумма.

Руководитель может создавать, редактировать и отменять заказы. Форма создания заказа (модальное окно) позволяет указать клиента (автодополнение по существующим), выбрать товары из каталога, установить дедлайн, ввести сумму и аванс. При сохранении задачи создаются автоматически.

Мастер видит те же заказы, но кнопки «Создать» и «Удалить» отсутствуют.

#### 2.1.3.8 Производственная панель: стек задач

Вкладка «Задачи» отображает два раздела: «Стек» (доступные задачи) и «В работе» (задачи, взятые текущим мастером).

Мастер видит в стеке только задачи по направлениям, к которым у него есть допуск. Каждая карточка задачи содержит: направление (тип работы), названия изделий в составе заказа, имя клиента. Кнопка «Взять в работу» переводит задачу из стека в раздел «В работе».

В разделе «В работе» мастер может вернуть задачу в стек или отметить её выполненной. При отметке выполнения система автоматически пересчитывает статус заказа.

Руководитель видит все задачи по всем направлениям.

#### 2.1.3.9 Производственная панель: матрица допусков

Вкладка «Допуски» доступна только руководителю. Отображается таблица: строки — мастера (все пользователи с флагом is_staff), столбцы — направления работ (Металл, Кольчуга, Кожа, Латунь, Дерево). На пересечении строки и столбца — переключатель (toggle), показывающий, имеет ли данный мастер допуск к данному направлению.

Руководитель может в один клик выдать или отозвать допуск. Изменение немедленно отражается на видимости задач в стеке соответствующего мастера.

#### 2.1.3.10 Адаптивный дизайн

Публичная часть сайта адаптирована для экранов от 375 пикселей (смартфон) до 2560 пикселей (широкоформатный монитор). Реализовано с помощью CSS Grid и медиазапросов:

- На экранах шире 1024 пикселей: трёхколонная сетка товаров, панель фильтров слева.
- На экранах 768–1023 пикселей: двухколонная сетка, панель фильтров сворачивается в кнопку.
- На экранах уже 767 пикселей: одноколонная сетка, фильтры в выдвижной панели (drawer).

Производственная панель оптимизирована для настольных экранов, но функционирует на планшетах с шириной от 768 пикселей: канбан-доска допускает горизонтальную прокрутку, таблица допусков — горизонтальный скролл контейнера.
