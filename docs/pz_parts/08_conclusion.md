# ЗАКЛЮЧЕНИЕ

В ходе выпускной квалификационной работы спроектировано и реализовано полнофункциональное веб-приложение «Кузница Кальрадия», объединяющее публичный тематический каталог средневекового снаряжения с закрытой системой управления производством мастерской.

Анализ предметной области показал, что деятельность ремесленной мастерской по производству исторического снаряжения предъявляет специфические требования, которые не удовлетворяет ни один из рассмотренных готовых программных продуктов: ни e-commerce платформы (WooCommerce, Shopify), ориентированные на серийную торговлю, ни CRM-системы (Битрикс24, amoCRM), не имеющие производственного модуля, ни системы управления задачами (Trello, Jira), функционирующие в отрыве от клиентской базы и каталога. Это обосновало целесообразность разработки собственного специализированного решения.

В результате выполнения работы решены все поставленные задачи:

1) Проведён анализ предметной области мастерской; выявлены три взаимосвязанных проблемы: отсутствие публичного каталога, неавтоматизированное управление производственными заказами и разрыв между публикациями в ВКонтакте и Telegram-аудиторией.

2) Исследованы семь программных аналогов (WooCommerce, Shopify, Битрикс24, amoCRM, Trello, Jira, Craft CMS); ни один из них не обеспечивает одновременного выполнения всей совокупности требований.

3) Сформированы функциональные требования (35 позиций) и нефункциональные требования (производительность, безопасность, надёжность, адаптивность, совместимость, сопровождаемость, доступность).

4) Выбрана и обоснована архитектура «SPA + REST API» на основе сравнительного анализа трёх подходов; выбор обеспечивает отзывчивость интерфейса и чёткое разделение ответственности между фронтендом и бэкендом.

5) Спроектирована структура базы данных (10 моделей), REST API (22 эндпоинта) и пользовательский интерфейс для двух групп пользователей.

6) Реализована серверная часть на Django 5.2 с Django REST Framework 3.16; реализованы алгоритмы начальной загрузки данных, автоматической генерации задач при создании заказа, матрицы допусков мастеров, репоста ВКонтакте → Telegram и email-уведомлений о дедлайнах.

7) Реализована клиентская часть — одностраничное приложение на React 19 с TypeScript; клиентская фильтрация каталога выполняется без обращения к серверу через useMemo; реализованы лайтбокс галереи, канбан-доска заказов, стек задач и матрица допусков.

8) Реализована интеграция с ВКонтакте Callback API и Telegram Bot API; новые публикации из группы ВКонтакте автоматически пересылаются в Telegram-канал с текстом и фотографиями.

9) Обеспечена защита от основных веб-угроз: CSRF-токены на всех небезопасных методах, httpOnly session cookie, проверка подписи webhook-запросов, хранение секретов в переменных окружения.

10) Разработаны 86 автоматических тестов; покрытие серверного кода составляет 89,7%, что превышает установленный порог в 80%.

11) Приложение развёрнуто на VPS-сервере под управлением Debian 11; стек продакшн-развёртывания: Gunicorn + Nginx + systemd с автоматическим перезапуском при сбое.

**Практическая значимость** разработки подтверждена реальной эксплуатацией: система запущена в промышленное использование мастерской. По итогам первых месяцев работы зафиксированы следующие результаты:
- Время оформления нового заказа сократилось с 15–20 минут (разрозненные записи в мессенджере и таблице Excel) до 3–5 минут (структурированная форма в системе).
- Потери задач при передаче между мастерами ликвидированы: каждая задача имеет явного исполнителя и статус.
- Потенциальные клиенты получили круглосуточный доступ к актуальному каталогу с полными характеристиками изделий, историческими справками и фотогалереями.
- Публикации в ВКонтакте автоматически дублируются в Telegram, что расширило охват аудитории без дополнительных трудозатрат.

**Возможные направления развития системы** включают: добавление аналитического раздела для руководителя (загруженность мастеров, средний срок выполнения заказов по типам); интеграцию с мессенджером для автоматического уведомления клиента о готовности заказа; возможный переход на PostgreSQL при росте объёма данных; реализацию мобильного приложения на основе существующего REST API.
