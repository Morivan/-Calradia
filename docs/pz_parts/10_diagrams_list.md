## Диаграмма 1 — Сравнение архитектурных подходов
**Место в тексте:** Раздел 1.3.1.1, после описания SSR / MPA / SPA  
**Подпись:** «Рисунок 1 — Сравнение архитектурных подходов: SSR, MPA+AJAX, SPA+REST API»  
**Содержание:** Три столбца, в каждом — схема взаимодействия браузер ↔ сервер. Для SSR: сервер генерирует HTML при каждом запросе. Для MPA+AJAX: сервер генерирует HTML, плюс отдельные AJAX-запросы. Для SPA: сервер возвращает статику один раз, далее только API-запросы.

## Диаграмма 4 — Алгоритм создания заказа и генерации задач
**Место в тексте:** Раздел 1.3.1.4 / 2.1.2.2, после описания алгоритма  
**Подпись:** «Рисунок 4 — Блок-схема алгоритма создания заказа и автоматической генерации задач»  
**Содержание:** Блок-схема (ГОСТ 19.701):
1. Начало
2. Получение данных POST-запроса
3. Валидация → нет client_name? → HTTP 400
4. Поиск клиента по имени → не найден? → создать клиента
5. Создание записи Order
6. Привязка товаров к заказу
7. Для каждого товара: определить категорию → маппинг на Direction
8. Создать Task для каждого уникального Direction (если не существует)
9. _sync_order_status(order)
10. Вернуть HTTP 201, данные заказа
11. Конец  
**Рекомендуемый инструмент:** draw.io (flowchart)

## Диаграмма 5 — Алгоритм проверки допуска при взятии задачи
**Место в тексте:** Раздел 1.3.1.5 / 2.1.2.3, после описания алгоритма  
**Подпись:** «Рисунок 5 — Блок-схема алгоритма проверки допуска мастера»  
**Содержание:** Блок-схема:
1. Начало: PATCH /api/workshop/tasks/{id}/
2. Авторизован? → нет → HTTP 401
3. Задача существует? → нет → HTTP 404
4. action == "take"?
5. is_superuser? → нет → проверить MasterApproval → нет допуска → HTTP 403
6. Статус задачи == "stack"? → нет → HTTP 400
7. Взять задачу (assigned_to = текущий пользователь, status = "in_progress")
8. HTTP 200
9. Конец  
**Рекомендуемый инструмент:** draw.io (flowchart)

## Диаграмма 6 — Алгоритм репоста ВКонтакте → Telegram
**Место в тексте:** Раздел 1.3.1.6 / 2.1.2.4, после описания алгоритма  
**Подпись:** «Рисунок 6 — Блок-схема алгоритма репоста публикации ВКонтакте в Telegram»  
**Содержание:** Блок-схема:
1. Начало: POST /api/vk/callback/
2. Проверка секрета → не совпадает → HTTP 403
3. Тип события == "confirmation"? → вернуть строку подтверждения
4. Тип события == "wall_post_new"?
5. Пост рекламный (marked_as_ads)? → пропустить → вернуть "ok"
6. VKPost уже существует по vk_id? → дубль → вернуть "ok"
7. Создать запись VKPost
8. parse_post() → text, photos
9. Отправить в Telegram → ошибка? → записать в лог → всё равно вернуть "ok"
10. Вернуть "ok" (HTTP 200)
11. Конец  
**Рекомендуемый инструмент:** draw.io (flowchart)

## Диаграмма 7 — Диаграмма вариантов использования (Use Case)
**Место в тексте:** Раздел 1.3.2 (взаимодействие с пользователем)  
**Подпись:** «Рисунок 7 — Диаграмма вариантов использования системы»  
**Содержание:** UML Use Case. Акторы: Посетитель, Мастер, Руководитель. Варианты использования:

- Руководитель (extends Мастер): Управлять каталогом, Управлять допусками, Удалять заказы, Управлять клиентами.  
**Рекомендуемый инструмент:** PlantUML / draw.io (UML)

## Диаграмма 8 — Последовательность инициализации приложения
**Место в тексте:** Раздел 1.3.1.3 (алгоритм инициализации)  
**Подпись:** «Рисунок 8 — Диаграмма последовательности инициализации SPA»  
**Содержание:** UML Sequence Diagram. Участники: Браузер, Nginx, Django, SQLite.
1. Браузер → Nginx: GET /
2. Nginx → Браузер: index.html + bundle.js
3. Браузер → Nginx: GET /api/csrf/ (параллельно с 4 и 5)
4. Браузер → Nginx: GET /api/bootstrap/
5. Браузер → Nginx: GET /api/auth/me/
6. Nginx → Django: проксирование запросов
7. Django → SQLite: запросы к БД
8. Django → Браузер: CSRF cookie / данные каталога / 401 (не авторизован)
9. Браузер: рендер каталога  
**Рекомендуемый инструмент:** PlantUML / draw.io (sequence)
