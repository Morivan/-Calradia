## 2.2 Тестирование программного обеспечения

### 2.2.1 Стратегия тестирования

Тестирование системы охватывает два уровня: модульное (unit) тестирование изолированных функций и интеграционное тестирование эндпоинтов API совместно с базой данных.

Для серверной части применён фреймворк Django TestCase, предоставляющий встроенный тестовый клиент (Client) и механизм транзакционной изоляции: каждый тест выполняется в отдельной транзакции, откатываемой после завершения, что исключает влияние одного теста на другие. Для мокирования внешних HTTP-вызовов (Telegram API, ВКонтакте) используется стандартная библиотека unittest.mock.

Для клиентской части применён фреймворк Vitest совместно с @testing-library/react. Тесты рендерят компоненты в виртуальном DOM (jsdom) и проверяют наличие ожидаемых элементов через запросы по тексту, роли и атрибутам, соответствующие реальному использованию компонента.

Выполнение всех тестов автоматизировано: серверные тесты запускаются командой `python manage.py test`, клиентские — командой `npm test`.

### 2.2.2 Модульные тесты

Модульные тесты расположены в файле `workshop/tests/test_unit.py`. Тестируются изолированные функции без обращения к базе данных и внешним сервисам.

**Модуль services/telegram.py.** Тестируются четыре сценария:
- Функция `get_api_base()` выбрасывает ValueError при отсутствии токена бота в настройках.
- Функция `get_api_base()` возвращает корректный URL при наличии токена.
- Функция `send_message()` выполняет POST-запрос с ожидаемым JSON-телом (имитация через `unittest.mock.patch`).
- Функция `store_update()` возвращает None для неподдерживаемых типов событий Telegram (несобственные сообщения, команды).

**Модуль services/vk.py.** Тестируются пять сценариев парсинга поста:
- Пост без вложений: извлекается только текст, список фото пуст.
- Пост с фотографиями: URL фотографий извлекаются корректно, выбирается максимальное разрешение.
- Пост с упоминаниями (@club...): упоминания удаляются из текста.
- Длинный текст (> 1000 символов): текст обрезается, добавляется многоточие.
- Подпись к альбому (текст при наличии фото): аналогичное обрезание.

**Сериализаторы.** Тестируется корректность отображения полей из snake_case (Python) в camelCase (JSON) для ProductSerializer и ReviewSerializer. Проверяется наличие обязательных полей badge и gallery в ответе.

**Вспомогательные функции views.py.** Тестируется функция `_product_kwargs()`: корректное маппирование входящих camelCase-ключей JSON в snake_case-поля модели; игнорирование неизвестных ключей (защита от перезаписи произвольных полей). Тестируется функция `_unique_slug()`: строчные буквы, длина не более 50 символов, уникальность при повторных вызовах.

### 2.2.3 Интеграционные тесты

Интеграционные тесты расположены в файле `workshop/tests/test_integration.py`. Каждый тестовый класс охватывает один модуль функциональности и проверяет взаимодействие представлений, сериализаторов и базы данных.

**BootstrapIntegrationTests.** Три сценария:
- GET /api/bootstrap/ возвращает HTTP 200 с объектом, содержащим поля products, reviews и links.
- Поле links содержит ожидаемые ключи (vk, telegram, email).
- При наличии записи IntegrationLink в базе её значение используется вместо дефолта из settings.

**ReviewIntegrationTests.** Два сценария:
- POST /api/products/{id}/reviews/ создаёт отзыв и возвращает HTTP 201.
- Запрос к несуществующему товару возвращает HTTP 404.

**ProductCRUDIntegrationTests.** Восемь сценариев:
- Анонимный GET /api/products/ возвращает HTTP 200.
- POST требует авторизации (HTTP 403 для анонима).
- Авторизованный POST создаёт товар, возвращает HTTP 201.
- PATCH обновляет поле товара.
- DELETE удаляет товар.
- PATCH без авторизации возвращает HTTP 403.
- GET /api/products/{id}/ для несуществующего ID возвращает HTTP 404.

**AuthIntegrationTests.** Пять сценариев:
- Вход с корректными учётными данными возвращает данные пользователя.
- Вход с неверным паролем возвращает HTTP 401.
- GET /api/auth/me/ без авторизации возвращает HTTP 401.
- После входа GET /api/auth/me/ возвращает данные пользователя.
- После выхода (POST /api/auth/logout/) сессия завершается.

**VkCallbackIntegrationTests.** Четыре сценария:
- Событие confirmation возвращает строку подтверждения.
- Запрос с неверным секретом возвращает HTTP 403.
- Событие wall_post_new вызывает функцию репоста (проверяется через mock).
- Событие wall_post_new с marked_as_ads=1 не вызывает репост.

**TaskApprovalIntegrationTests.** Девять сценариев — наиболее полно покрытый модуль:
- Мастер без допуска не может взять задачу по данному направлению (HTTP 403).
- Мастер с допуском успешно берёт задачу (HTTP 200).
- Повторное взятие уже занятой задачи возвращает HTTP 400.
- Мастер может вернуть свою задачу в стек.
- Мастер может отметить свою задачу выполненной.
- Неавторизованный пользователь не может взять задачу (HTTP 401).
- Суперпользователь может взять задачу без допуска.
- Суперпользователь может выдать допуск мастеру.
- Суперпользователь может отозвать допуск.
- Не-суперпользователь не может управлять допусками (HTTP 403).

**WorkshopOrderIntegrationTests.** Шесть сценариев:
- Неавторизованный пользователь не может просматривать заказы.
- Мастер (is_staff) может просматривать список заказов.
- Мастер может создавать заказ.
- Попытка создания заказа без обязательного поля client_name возвращает HTTP 400.
- Мастер может редактировать свой заказ (PATCH).
- Суперпользователь может удалять заказы; не-суперпользователь — нет.

**ProductSetCatalogIntegrationTests.** Пять сценариев:
- Список комплектов публично доступен (HTTP 200).
- Детальная страница комплекта доступна по slug.
- Запрос по несуществующему slug возвращает HTTP 404.
- Товары в составе комплекта содержат поле price.

**NotifyUrgentOrdersCommandTests.** Два сценария:
- Команда в режиме --dry-run выводит заказы с дедлайном через 14, 7 и 3 дня.
- В режиме --dry-run письма не отправляются.

**ReviewAuthorIntegrationTests.** Два сценария:
- Отзыв с указанным именем автора сохраняет его в базе.
- Отзыв без имени автора сохраняется с пустой строкой.

### 2.2.4 Клиентские тесты

Клиентские тесты расположены в директории `src/test/` (FiltersPanel.test.tsx, HomePage.test.tsx, ProductCard.test.tsx, SortControl.test.tsx).

Тесты рендерят компоненты в изолированном окружении (jsdom) с тестовыми данными, идентичными по структуре продуктовому каталогу. Проверяется:

- **ProductCard:** отображение названия, цены, исторического периода; наличие значка скидки при соответствующих данных; корректный переход при клике.
- **FiltersPanel:** наличие полей для каждого типа фильтра; сброс фильтров при нажатии кнопки «Сбросить».
- **SortControl:** отображение текущей выбранной опции; вызов колбэка при изменении.
- **HomePage:** отображение карточек товаров при наличии данных; пустое состояние при пустом массиве.

### 2.2.7 Ручное тестирование

Помимо автоматических тестов, система прошла ручное функциональное тестирование в браузерах Chrome 124, Firefox 126 и Safari 17 (macOS). Проверялись следующие сценарии:

1. Полный жизненный цикл заказа: создание → генерация задач → взятие задач мастерами → выполнение → автоматическое обновление статуса.
2. Репост публикации из группы ВКонтакте в Telegram: публикация поста с текстом и несколькими фотографиями.
3. Email-уведомление: создание заказа с дедлайном через 14 дней, ручной запуск команды notify_urgent_orders, проверка доставки письма.
4. Адаптивность: тестирование публичного каталога на экранах 375px, 768px, 1280px, 1920px.
5. Безопасность: попытка доступа к /workshop без авторизации (редирект на /login); попытка PATCH /api/products/ без CSRF-токена (HTTP 403); попытка взять задачу без допуска (HTTP 403).

Все сценарии выполнились ожидаемым образом. Замечаний не выявлено.
