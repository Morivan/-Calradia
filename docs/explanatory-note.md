## 2. Введение

Современный рынок ремесленных изделий и исторической реконструкции активно развивается: растёт интерес к средневековой культуре, живым историческим фестивалям и ролевым играм. Мастерские, изготавливающие доспехи, оружие и элементы исторического костюма, нуждаются в инструментах для представления своих изделий потенциальным клиентам и организации производственных процессов.

Ручное ведение заказов (записные книжки, таблицы Excel, переписка в мессенджерах) не обеспечивает прозрачности, приводит к потере информации и ошибкам при распределении работы между мастерами. Отсутствие публичного каталога с фотографиями, характеристиками и историческими сведениями снижает конкурентоспособность мастерской.

Данная работа посвящена проектированию и реализации веб-приложения «Кузница Кальрадия» — системы, совмещающей публичный онлайн-каталог изделий с внутренней панелью управления мастерской, включающей модули заказов, задач, клиентской базы и распределения работ между мастерами.

**Актуальность** работы обусловлена отсутствием на рынке готовых решений, ориентированных на малые ремесленные производства с системой специализации мастеров.

**Цель работы** — разработать полнофункциональное веб-приложение, сочетающее публичный каталог товаров и закрытую систему управления мастерской.

**Задачи:**

1. Проанализировать существующие решения в области e-commerce и систем управления заказами.
2. Спроектировать архитектуру клиент-серверного SPA с REST API.
3. Реализовать модели данных, охватывающие производственный процесс мастерской.
4. Разработать публичный каталог с фильтрацией, поиском и детальными карточками товаров.
5. Разработать панель управления: заказы (канбан), задачи, клиентская база, допуски мастеров.
6. Обеспечить интеграцию с ВКонтакте и Telegram для автопубликации новостей.
7. Обеспечить безопасность: аутентификация, CSRF-защита, контроль доступа.
8. Провести функциональное тестирование системы.

## 3. Постановка задачи

### 3.1 Назначение системы

Разрабатываемая система предназначена для двух категорий пользователей:

**Посетители сайта** — потенциальные клиенты мастерской. Им доступны: просмотр каталога изделий с фильтрацией и поиском, детальная карточка каждого изделия (галерея, характеристики, историческая справка, цена), просмотр новостей из группы ВКонтакте, переход в чат ВКонтакте для оформления заказа.

**Сотрудники мастерской** — руководитель и мастера. После авторизации им доступна закрытая панель управления с разграничением прав:

- **Руководитель (суперадмин)** — полный доступ: создание/удаление заказов, управление каталогом, назначение мастеров, управление допусками.
- **Мастер (is_staff)** — доступ к задачам по своим допускам, просмотр своих заказов, обновление статусов задач.

### 3.2 Требования к функциональности

**Публичный каталог:**
- Отображение товаров в адаптивной сетке
- Фильтрация по категории, материалу, эпохе, размеру, статусу
- Полнотекстовый поиск по названию
- Сортировка: по умолчанию, по дате, по популярности, по сроку изготовления
- Детальная карточка с галереей и лайтбоксом
- Каталог комплектов со скидочной ценой
- Оставление отзывов (без авторизации)

**Панель мастерской:**
- Сводная страница: счётчики заказов, горящие дедлайны, предупреждения о малом запасе материалов
- Канбан-доска заказов (Новый / В работе / Выполнен / Отменён)
- Создание заказа с автоматическим расчётом аванса (50%) и созданием задач
- Управление клиентской базой
- Система задач: стек доступных задач, взятие в работу, закрытие
- Управление допусками мастеров к конкретным изделиям
- CRUD-операции с каталогом товаров

**Интеграции:**
- Автоматический репост новых записей со стены ВКонтакте в Telegram-канал
- Email-уведомления о дедлайнах (за 14, 7, 3, 1 день)

### 3.3 Требования к надёжности и безопасности

- Аутентификация на основе сессий Django (httpOnly cookies)
- CSRF-защита для всех небезопасных HTTP-методов
- Разграничение прав: публичный доступ / `is_staff` / `is_superuser`
- Валидация входных данных на стороне сервера
- Защита от несанкционированного изменения чужих заказов
- Хранение конфигурационных секретов в переменных окружения, исключение `.env` из репозитория

## 4. Обзор существующих решений

### 4.1 Универсальные e-commerce платформы

**WooCommerce** (плагин WordPress) и **Shopify** предоставляют готовые решения для интернет-торговли. Однако они ориентированы на стандартный товарный каталог с корзиной и оплатой онлайн, тогда как для мастерской критична возможность обсуждения и настройки каждого изделия под клиента. Кроме того, обе платформы не имеют встроенных инструментов для управления производственными задачами и распределения работ между мастерами.

### 4.2 CRM-системы

**Битрикс24** и **amoCRM** охватывают управление клиентами и сделками, но избыточны для малой мастерской: сложны в настройке, требуют значительных расходов на подписку, не имеют публичного каталога с историческими сведениями об изделиях.

### 4.3 Системы управления задачами

**Trello** и **Jira** решают задачу визуализации работ, но не интегрированы с каталогом товаров и клиентской базой, что требует дублирования данных.

### 4.4 Вывод

Ни одно из существующих решений не объединяет в одной системе: публичный тематический каталог с историческими справками, управление производственными заказами и систему специализации мастеров (допуски). Разработка собственного приложения является обоснованной.

## 5. Проектирование системы

### 5.1 Выбор технологий

#### Бэкенд

Для реализации серверной части выбран **Django 5** с **Django REST Framework (DRF)**:

- Django предоставляет зрелую ORM, встроенную систему аутентификации, миграции, административный интерфейс.
- DRF упрощает создание REST API: сериализаторы, аутентификация, разграничение доступа.
- Python широко применяется в учебном процессе и имеет богатую экосистему.

Язык: **Python 3.12**.

Хранение статических файлов: **WhiteNoise** — позволяет отдавать статику непосредственно из Django/Gunicorn без отдельного Nginx-правила для файлов, с Brotli-сжатием.

#### Фронтенд

Для реализации клиентской части выбран **React 18** с **TypeScript**:

- React обеспечивает декларативный подход к построению UI и реактивное обновление компонентов.
- TypeScript добавляет статическую типизацию, снижая количество ошибок при разработке.
- **Vite 5** — современный инструмент сборки с быстрым dev-сервером и HMR (Hot Module Replacement).
- **Lucide React** — минималистичный набор SVG-иконок.

Стилизация: чистый CSS с CSS custom properties (переменные), без UI-фреймворков — для полного контроля над внешним видом.

#### База данных

В разработке используется **SQLite** (встроена в Python, не требует установки). В продакшне рекомендуется **PostgreSQL** для большей надёжности и поддержки конкурентного доступа.

#### Веб-сервер

**Nginx + Gunicorn**: Nginx принимает HTTP-запросы, отдаёт статические файлы и проксирует динамические запросы на Gunicorn, который запускает WSGI-приложение Django.

### 5.2 Архитектура приложения

Приложение построено по **клиент-серверной архитектуре** с паттерном **SPA (Single Page Application)**:

```
┌─────────────────────────────────────────────────────────────┐
│                      Браузер клиента                         │
│                                                              │
│    React 18 SPA                                              │
│    ┌─────────────┐  ┌────────────────┐  ┌────────────────┐  │
│    │   Каталог   │  │ Панель         │  │  Карточка      │  │
│    │   товаров   │  │ мастерской     │  │  товара        │  │
│    └─────────────┘  └────────────────┘  └────────────────┘  │
└────────────────────────────┬────────────────────────────────┘
                              │  HTTPS / JSON API (/api/*)
                              │  Сессионная cookie + CSRF
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                         Nginx                                │
│   /static/*  → WhiteNoise (собранный фронтенд + статика)    │
│   /api/*     → Gunicorn → Django                            │
│   /*         → index.html  (SPA-роутинг)                    │
└────────────────────────────┬────────────────────────────────┘
                              │
┌─────────────────────────────▼───────────────────────────────┐
│                    Django + DRF                              │
│                                                              │
│  workshop/views.py                                           │
│  ┌─────────────┐  ┌──────────────┐  ┌──────────────────┐   │
│  │  Публичный  │  │   Workshop   │  │   Вебхуки        │   │
│  │  API        │  │   API        │  │   VK / Telegram  │   │
│  └──────┬──────┘  └──────┬───────┘  └─────────┬────────┘   │
│         └────────────────┼──────────────────────┘           │
│                          │ ORM                              │
│                          ▼                                  │
│              workshop/models.py  →  SQLite / PostgreSQL      │
└─────────────────────────────────────────────────────────────┘
```

**Инициализация данных.** При загрузке приложения фронтенд выполняет один запрос `GET /api/bootstrap/`, получая сразу все товары, отзывы и внешние ссылки. Это минимизирует число round-trip запросов при первом рендере.

**Аутентификация.** Используется стандартная Django-сессия: при успешном входе сервер устанавливает `sessionid` (httpOnly cookie). Все небезопасные запросы (POST, PATCH, DELETE) требуют заголовок `X-CSRFToken`.

### 5.3 Модели данных

Диаграмма ключевых связей между моделями:

```
Product ──────────────────────── MasterApproval ──── User (мастер)
   │                                    │
   │ (M2M)                              │
   ├──── ProductSet                     │
   │                               Task ──── Order ──── Client
   │                                            │
   └──────────────────────────────── Order ─────┘
```

**Описание моделей:**

| Модель | Назначение | Ключевые поля |
|--------|-----------|---------------|
| `Product` | Изделие каталога | `slug`, `name`, `category`, `status`, `price_from`, `sizes` (JSON), `gallery` (JSON) |
| `ProductSet` | Комплект из нескольких изделий | `slug`, `name`, `products` (M2M к Product), `price_from` |
| `Review` | Отзыв покупателя | `product` (FK), `author`, `rating` (1–5), `text` |
| `Client` | Клиент мастерской | `name`, `vk_url`, `status` (Потенциальный / Действующий / Завершён) |
| `Order` | Заказ | `client` (FK), `order_type` (product/set/service), `status`, `total`, `advance`, `deadline`, `assigned_to` (FK User) |
| `Task` | Производственная задача | `order` (FK), `product` (FK), `status` (pending/taken/done), `assigned_to` (FK User) |
| `MasterApproval` | Допуск мастера | `master` (FK User), `product` (FK) |
| `Material` | Материал на складе | `type`, `stock`, `min_stock`, `price` |
| `VKPost` | Пост из ВКонтакте | `post_id`, `text`, `photo_url`, `posted_at` |
| `IntegrationLink` | Внешние ссылки | `key`, `label`, `url` |

Все модели (кроме `MasterApproval` и `VKPost`) наследуют абстрактный `TimestampedModel` с полями `created_at` и `updated_at` (`auto_now_add` / `auto_now`).

### 5.4 Проектирование API

API построено по принципам REST. Все ответы в формате JSON.

**Публичные эндпоинты (без авторизации):**

| Метод | URL | Описание |
|-------|-----|----------|
| `GET` | `/api/bootstrap/` | Загрузка каталога, отзывов и ссылок |
| `GET` | `/api/catalog/products/` | Список товаров |
| `GET` | `/api/catalog/products/{id}/` | Карточка товара |
| `POST` | `/api/catalog/products/{id}/reviews/` | Оставить отзыв |
| `GET` | `/api/vk-posts/` | Список постов из ВКонтакте |
| `POST` | `/api/auth/login/` | Вход в систему |
| `POST` | `/api/auth/logout/` | Выход |
| `GET` | `/api/auth/me/` | Данные текущего пользователя |

**Эндпоинты мастерской (требуют `is_staff`):**

| Метод | URL | Описание |
|-------|-----|----------|
| `GET` | `/api/workshop/dashboard/` | Сводная статистика |
| `GET/POST` | `/api/workshop/orders/` | Заказы |
| `PATCH/DELETE` | `/api/workshop/orders/{id}/` | Обновление/удаление заказа |
| `POST` | `/api/workshop/orders/create/` | Создание заказа с авто-ценой |
| `GET/POST` | `/api/workshop/clients/` | Клиентская база |
| `PATCH` | `/api/workshop/clients/{id}/` | Обновление клиента |
| `GET/POST` | `/api/workshop/sets/` | Комплекты |
| `GET` | `/api/workshop/tasks/` | Задачи (параметр `view`: `stack`/`mine`) |
| `PATCH` | `/api/workshop/tasks/{id}/` | Действие над задачей |
| `GET/POST` | `/api/workshop/approvals/` | Допуски мастеров |
| `GET` | `/api/workshop/users/` | Список сотрудников |
| `POST/PATCH/DELETE` | `/api/catalog/products/` и `/{id}/` | Управление каталогом |

**Вебхуки:**

| Метод | URL | Описание |
|-------|-----|----------|
| `POST` | `/api/integrations/vk/callback/` | Callback API ВКонтакте |
| `POST` | `/api/integrations/telegram/webhook/` | Вебхук Telegram-бота |

### 5.5 Проектирование пользовательского интерфейса

Интерфейс разработан с учётом двух целевых аудиторий:

**Публичная часть** — стилизована под «средневековую кузницу»: тёмная цветовая схема (`#1a1a12` — фон, `#c1c8bc` — текст), акцентный бордовый цвет (`#a13333`), гарнитура с засечками для заголовков, элементы состаренной бумаги. Цель — создать атмосферу, соответствующую тематике изделий.

**Панель мастерской** — функциональный интерфейс с тёмной темой, читаемым шрифтом без засечек, минималистичными элементами управления. Приоритет — скорость работы и информативность.

Адаптивная вёрстка обеспечивает корректное отображение на устройствах с шириной экрана от 375 px (смартфон) до 1920 px (настольный монитор). Канбан-доска на мобильных устройствах прокручивается горизонтально.

### 6.2 Бэкенд

Все вьюхи реализованы как классы на основе `APIView` из Django REST Framework. Это обеспечивает явный контроль над обработкой каждого HTTP-метода:

```python
class WorkshopOrderCreateView(APIView):
    def post(self, request):
        if not _is_staff(request):
            return Response(
                {"detail": "Требуется авторизация."},
                status=status.HTTP_401_UNAUTHORIZED
            )
        # ...логика создания заказа
```

#### Вспомогательные функции

Для обеспечения безопасности и единообразия в `views.py` выделены хелперы:

```python
def _is_staff(request) -> bool:
    return request.user.is_authenticated and request.user.is_staff

def _parse_int(value, default: int = 0) -> int:
    try:
        return int(value or default)
    except (ValueError, TypeError):
        return default

def _parse_deadline(raw) -> datetime.date | None:
    for fmt in ("%Y-%m-%d", "%d.%m.%Y"):
        try:
            return datetime.strptime(str(raw), fmt).date()
        except (ValueError, TypeError):
            pass
    return None
```

Функция `_parse_int` предотвращает ошибки 500 при передаче некорректных числовых значений (например, строки вместо числа в поле суммы заказа).

#### Bootstrap-эндпоинт

`BootstrapView` формирует ответ, объединяющий данные из нескольких таблиц БД в одном JSON-объекте. Это исключает необходимость нескольких параллельных запросов при загрузке страницы:

```python
payload = {

    "links": {
        "telegramOrder": links.get("telegram_order", settings.TELEGRAM_PUBLIC_URL),
        "vkCommunity": links.get("vk_community", settings.VK_COMMUNITY_URL),
        # ...
    },

```

#### Сериализаторы

DRF-сериализаторы (`ProductSerializer`, `ReviewSerializer`, `IntegrationLinkSerializer`) обеспечивают преобразование объектов Django-моделей в JSON и обратно с автоматической валидацией типов.

#### HTTP-клиент

Функция `apiFetch` в `src/api.ts` централизует логику HTTP-запросов: добавляет заголовок `Content-Type: application/json`, автоматически извлекает CSRF-токен из cookie и устанавливает `credentials: 'include'` для передачи сессионной cookie:

```typescript
export async function apiFetch(
    url: string,
    options: RequestInit = {}
): Promise<Response> {
    const method = (options.method ?? 'GET').toUpperCase();
    const headers: Record<string, string> = {
        'Content-Type': 'application/json',
        ...(options.headers as Record<string, string>)
    };
    if (method !== 'GET' && method !== 'HEAD') {
        headers['X-CSRFToken'] = getCsrfToken();
    }
    return fetch(url, { ...options, headers, credentials: 'include' });
}
```

#### Компонент WorkshopPanel

Панель мастерской реализована как единый компонент `WorkshopPanel.tsx`, разделённый на именованные вкладки. Каждая вкладка содержит собственную логику загрузки данных и отображения.

Канбан-доска реализована через группировку заказов по полю `status` с возможностью перетаскивания карточек (Drag and Drop) между колонками.

При сборке командой `npm run build` Vite генерирует оптимизированные статические файлы в директорию `dist/`. Django подключает эту директорию как источник статических файлов (`STATICFILES_DIRS`), а WhiteNoise раздаёт их с Brotli-сжатием и долгосрочным кэшированием.

### 6.4 Система задач и допусков мастеров

Система задач — ключевая производственная функция приложения. Алгоритм работы:

1. Руководитель создаёт заказ через `WorkshopOrderCreateView`.
2. Метод `_create_tasks_for_order(order)` автоматически генерирует задачи:
   - Тип «предмет» → одна задача на изделие
   - Тип «комплект» → по одной задаче на каждый предмет в комплекте
   - Тип «услуга» → одна задача с названием из поля `product_name`
3. Задачи попадают в стек со статусом `pending`.
4. Мастер открывает вкладку «Задачи» и видит только те задачи, к изделиям которых у него есть допуск (`MasterApproval`):

```python
approved_product_ids = list(
    MasterApproval.objects.filter(master=request.user)
        .values_list('product_id', flat=True)
)
qs = qs.filter(product_id__in=approved_product_ids)
```

5. Мастер нажимает «Взять задачу» (`action: 'take'`): задача переходит в `taken`, назначается на него.
6. После выполнения работы мастер нажимает «Выполнено» (`action: 'done'`): задача переходит в `done`.

Такая система позволяет управлять специализацией: кузнец видит задачи на изготовление металлических деталей, кожевник — на кожаные элементы, не мешая друг другу.

### 6.5 Интеграции

#### ВКонтакте → Telegram

При публикации нового поста на стене группы ВКонтакте платформа отправляет POST-запрос на `/api/integrations/vk/callback/`. Обработчик `VkCallbackView`:

1. Проверяет секретный ключ `VK_CALLBACK_SECRET`.
2. Извлекает текст и фотографию из объекта `wall_post_new`.
3. Сохраняет пост в модель `VKPost` (для отображения в блоке новостей).
4. Пересылает пост в Telegram-канал через метод `repost_to_channel()`.

Для предотвращения дублирования используется кэш Django: ключ `vk_post_{owner_id}_{post_id}` с TTL 24 часа.

#### Email-уведомления о дедлайнах

Management-команда `notify_urgent_orders` отправляет письма ответственным мастерам и администратору за 14, 7, 3 и 1 день до дедлайна активных заказов. Команда запускается через cron раз в сутки.

### 6.6 Безопасность

Реализованы следующие меры защиты:

| Угроза | Контрмера |
|--------|----------|
| CSRF-атака | `CsrfViewMiddleware` + заголовок `X-CSRFToken` на клиенте |
| Несанкционированное изменение данных | Проверка `_is_staff()` / `is_superuser` в каждой вьюхе |
| Изменение чужого заказа | Проверка `order.assigned_to_id == request.user.id` |
| XSS | Экранирование выводимых данных реализует React (виртуальный DOM) |
| Утечка секретов | `.env` в `.gitignore`, секреты только в переменных окружения |
| Небезопасная передача данных | HTTPS в продакшне (Nginx + SSL), `Secure`-флаги на cookies при `USE_HTTPS=true` |
| Кликджекинг | `XFrameOptionsMiddleware` (Django по умолчанию) |
| Content sniffing | `SECURE_CONTENT_TYPE_NOSNIFF = True` в продакшне |

### 7.5 Обнаруженные и исправленные дефекты

В ходе тестирования были обнаружены и исправлены следующие ошибки:

1. **Ошибка 500 при некорректном числовом вводе.** При передаче строки в поля `advance_override`, `price_from` и `min_stock/price` сервер возвращал Internal Server Error из-за необработанного исключения `ValueError`. Исправлено: добавлены блоки `try/except` с возвратом ответа `400 Bad Request`.

2. **Несанкционированное изменение каталога.** Проверка доступа в `ProductListCreateView` и `ProductDetailView` использовала `is_authenticated` вместо `is_staff`, что позволяло любому авторизованному пользователю изменять товары. Исправлено: заменено на `_is_staff(request)`.

3. **Два conflicting CTA-элемента на карточке товара.** На карточке товара одновременно присутствовали кнопка «Связаться для заказа» (переход в VK) и модальное окно с формой заказа. Исправлено: оставлена единственная кнопка с прямым переходом в диалоги ВКонтакте.

## 8. Развёртывание

### 8.1 Сборка и деплой

Приложение развёртывается на VPS под управлением Ubuntu 24.04. Схема:

```
Git-репозиторий
      │
      │  git pull
      ▼
   VPS-сервер
      │
      ├─ npm run build     → dist/ (фронтенд)
      ├─ collectstatic     → staticfiles/ (статика Django)
      ├─ migrate           → обновление схемы БД
      └─ systemctl restart → Gunicorn перезапускается
```

Последовательность команд деплоя:

```bash
git pull
source venv/bin/activate
pip install -r requirements.txt
npm ci && npm run build
python manage.py collectstatic --noinput
python manage.py migrate
systemctl restart calradia
```

### 8.2 Конфигурация окружения

Все конфигурационные параметры вынесены в переменные окружения (файл `.env` на сервере). Файл не хранится в репозитории. Ключевые параметры:

- `DJANGO_SECRET_KEY` — криптографический ключ Django
- `DJANGO_DEBUG=false` — режим продакшна
- `DJANGO_ALLOWED_HOSTS` — разрешённые домены
- `USE_HTTPS=true` — включение `Secure`-флага на cookies
