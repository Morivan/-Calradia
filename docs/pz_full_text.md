# ТЕРМИНЫ И СОКРАЩЕНИЯ

**API** (Application Programming Interface) — программный интерфейс приложения; совокупность правил и протоколов, определяющих способ взаимодействия программных компонентов между собой.

**Backend (бэкенд)** — серверная часть веб-приложения, отвечающая за обработку запросов, бизнес-логику и работу с базой данных.

**Callback API** — механизм уведомления сервера о событиях путём отправки HTTP-запроса на заранее настроенный URL при возникновении события во внешней системе.

**CORS** (Cross-Origin Resource Sharing) — механизм, позволяющий или запрещающий веб-приложениям одного домена выполнять запросы к ресурсам другого домена.

**CSRF** (Cross-Site Request Forgery) — вид атаки, при которой вредоносный сайт заставляет браузер аутентифицированного пользователя выполнить нежелательный запрос к доверенному сайту.

**CRUD** (Create, Read, Update, Delete) — четыре базовые операции с данными: создание, чтение, изменение и удаление.

**DRF** (Django REST Framework) — расширение фреймворка Django для разработки REST API.

**Frontend (фронтенд)** — клиентская часть веб-приложения, выполняемая в браузере пользователя.

**GUI** (Graphical User Interface) — графический пользовательский интерфейс.

**HMR** (Hot Module Replacement) — технология замены изменённых модулей в браузере без полной перезагрузки страницы.

**JSON** (JavaScript Object Notation) — текстовый формат обмена данными, основанный на синтаксисе JavaScript-объектов.

**ORM** (Object-Relational Mapping) — технология преобразования данных между реляционной СУБД и объектно-ориентированной программой.

**REST** (Representational State Transfer) — архитектурный стиль создания распределённых гипермедиа-систем, ориентированный на работу с ресурсами через стандартные HTTP-методы.

**SPA** (Single Page Application) — одностраничное приложение; веб-приложение, которое при первом запросе загружает одну HTML-страницу и в дальнейшем обновляет её содержимое динамически, без полной перезагрузки.

**WSGI** (Web Server Gateway Interface) — стандарт взаимодействия между веб-сервером и Python-приложением.

**VPS** (Virtual Private Server) — виртуальный выделенный сервер.

**БД** — база данных.

**ВКР** — выпускная квалификационная работа.

**ПЗ** — пояснительная записка.

**ПО** — программное обеспечение.

**СУБД** — система управления базами данных.

# ВВЕДЕНИЕ

Ремесленное производство исторического снаряжения — один из немногих видов деятельности, в котором ручной труд и глубокие специальные знания остаются абсолютно незаменимыми. Мастерская «Кузница Кальрадия» занимается изготовлением доспехов, шлемов, нагрудников, кольчуг и сопутствующего снаряжения, воспроизводя образцы западноевропейского вооружения XIII–XVI веков. Продукция ориентирована на участников клубов исторической реконструкции, ролевых игр, театральных коллективов и частных коллекционеров — людей, для которых важны не только функциональность изделия, но и его историческая достоверность.

Именно специфика аудитории и производственного процесса делают мастерскую совершенно непохожей на обычный интернет-магазин. Клиент не просто выбирает товар из готового ассортимента: он обсуждает с мастером исторический прообраз, материалы, размеры, степень украшения и сроки. Каждый заказ уникален или почти уникален. Над одним заказом могут работать несколько мастеров с разными специализациями: кузнец отвечает за металлические элементы, кожевник — за подшлемник и поддоспешник, специалист по клёпке — за кольчужные детали. При этом далеко не каждый мастер квалифицирован для работы с любым изделием.

До появления специализированного программного обеспечения мастерская решала эти задачи подручными средствами: записями в мессенджерах, таблицами Excel и общими папками в облачном хранилище. Такой подход неизбежно порождает проблемы: информация о заказах теряется при смене телефона, мастера не знают, чем занимаются коллеги, руководитель не видит полной картины загруженности. Публичная часть — портфолио мастерской — и вовсе отсутствовала: потенциальные клиенты не могли заранее познакомиться с изделиями, материалами, ценами и сроками изготовления.

Параллельно существовала и коммуникационная проблема: активная группа ВКонтакте публиковала фотографии готовых работ и новости мастерской, но эти материалы не попадали автоматически на сайт и не дублировались в Telegram — более популярном мессенджере среди молодой аудитории.

Настоящая выпускная квалификационная работа направлена на решение совокупности описанных проблем. Её результатом является полнофункциональное веб-приложение «Кузница Кальрадия», состоящее из двух неотделимых частей: публичного онлайн-каталога и производственной панели управления. Каталог даёт потенциальным клиентам полное представление об ассортименте, исторических основах изделий и условиях работы с мастерской. Панель управления — это внутренний инструмент, автоматизирующий приём заказов, распределение задач по специализациям мастеров, ведение клиентской базы и отслеживание дедлайнов.

# Раздел 1 Теоретическая составляющая работы

## 1.1 Анализ предметной области, выявление аналогов

### 1.1.1 Описание предметной области

Предметная область настоящей работы — деятельность небольшой ремесленной мастерской, специализирующейся на изготовлении западноевропейских доспехов и снаряжения XIII–XVI веков. Ассортимент мастерской охватывает несколько десятков позиций: шлемы (бацинет, топфхельм, салад, армет, барбют), нагрудники и нагрудно-спинные комплекты, кольчужное полотно, бригантины, набедренники, поножи, рукавицы и полные рыцарские доспехи. Значительную часть продукции составляют комплекты снаряжения — наборы изделий, собранные по единому историческому образцу, от пехотного комплекта XIV века до полного латного доспеха XV века.

Клиенты мастерской делятся на несколько категорий: участники клубов военно-исторической реконструкции, которым требуется аутентичное снаряжение для фестивалей и турниров; участники ролевых игр и LARP-движения, которым важны внешний вид и безопасность; театральные коллективы и киностудии, заказывающие как реплики исторических образцов, так и стилизованные изделия; коллекционеры и частные лица, приобретающие доспех как предмет интерьера. Каждая из этих групп предъявляет специфические требования к изделию, что делает стандартизацию производства затруднённой, а каждый заказ — в значительной мере уникальным.

Производственный процесс организован следующим образом. Клиент обращается в мастерскую, чаще всего через социальную сеть ВКонтакте, и обсуждает с руководителем детали заказа: исторический прообраз, материал (сталь различных марок, кожа, латунь), степень полировки и украшения, антропометрические параметры. После согласования условий и внесения аванса заказ передаётся в производство. Разные элементы заказа выполняются разными специалистами: металлист куёт и формирует стальные части, кожевник изготавливает кожаный подклад и ремни, мастер по кольчуге плетёт кольчужное полотно. Каждый мастер работает с теми изделиями, к которым имеет квалификацию и опыт. По завершении работы изделие передаётся на контроль качества, упаковывается и доставляется клиенту.

Типичный производственный цикл от принятия заказа до отгрузки составляет от двух недель (для простых изделий) до трёх-шести месяцев (для полных рыцарских комплектов). В работе одновременно находится от пяти до двадцати заказов. Штат мастерской — три-семь человек плюс руководитель, причём часть мастеров может работать на условиях частичной занятости.

До разработки специализированного ПО управление заказами вели в смешанной системе: переписка с клиентами хранилась в истории диалогов ВКонтакте, производственные задачи назначались устно или через общий чат мессенджера, а сроки и финансовые данные записывались в таблицах Excel. Такая система была крайне уязвима к потере данных, не давала единого актуального состояния заказов и не позволяла строить аналитику. Публичного сайта-каталога не существовало вовсе: потенциальные клиенты изучали работы мастерской только через группу ВКонтакте.

Таким образом, задача автоматизации деятельности мастерской включает три взаимосвязанных компонента: публичное представление продукции (каталог), управление производственными заказами (CRM/ERP-элементы) и обеспечение коммуникации с аудиторией (интеграция с соцсетями).

### 1.1.2 Обзор и анализ существующих решений

На рынке существует ряд программных продуктов, потенциально применимых для решения одной или нескольких задач, стоящих перед мастерской. Ниже проведён детальный анализ наиболее релевантных из них.

#### WooCommerce

WooCommerce — плагин электронной коммерции для системы управления контентом WordPress, по данным компании Automattic занимающий около 28% рынка платформ интернет-торговли [1]. Платформа предоставляет полный набор инструментов для создания онлайн-магазина: каталог товаров, корзину, оформление заказа, интеграцию с платёжными шлюзами, управление запасами.

Применительно к мастерской средневекового снаряжения WooCommerce имеет существенные ограничения. Платформа ориентирована на серийную торговлю стандартизированными товарами с фиксированными ценами: в ней не предусмотрен механизм обсуждения и согласования заказа с клиентом, нет понятия «производственная задача» или «мастер со специализацией». Попытки адаптировать WooCommerce к нуждам мастерской потребовали бы множества плагинов (конфигуратор товаров, система заявок, управление задачами), что существенно усложнило бы поддержку и обновление. Кроме того, визуальный стиль WooCommerce-магазинов сложно настроить под специфическую тематическую стилистику, а тематические шаблоны «под средневековье», как правило, выглядят шаблонно и неубедительно.

#### Shopify

Shopify — облачная платформа электронной коммерции по подписной модели. Имеет схожие с WooCommerce функции, но предоставляется как услуга (SaaS): не требует собственного хостинга, но подразумевает ежемесячную оплату (от 29 до 299 долларов США в зависимости от тарифного плана) [2].

Для российского малого бизнеса работа с Shopify дополнительно осложнена ограничениями на использование платёжных систем и необходимостью рассчитываться в иностранной валюте. Фундаментальные же ограничения аналогичны WooCommerce: платформа не рассчитана на уникальное производство под заказ с производственными стадиями и специализациями исполнителей. Тематическая кастомизация ограничена доступными шаблонами.

#### Битрикс24

Битрикс24 — российская CRM-система с широким набором функций: управление контактами и сделками, канбан-доска задач, телефония, корпоративный мессенджер, конструктор сайтов [3]. Существует как в облачной версии (от 0 до 9 590 рублей в месяц), так и в коробочной (единоразовая лицензия).

CRM-модуль Битрикс24 потенциально подходит для ведения клиентской базы и заказов. Однако для мастерской с персоналом 5–10 человек бесплатного тарифа достаточно по функционалу, но интерфейс системы перегружен и требует значительного времени на освоение. Отдельной проблемой является отсутствие публичного каталога продукции — инструменты для создания сайта в Битрикс24 ориентированы на корпоративные порталы, а не на тематические витрины. Система задач в Битрикс24 универсальна, но не предусматривает понятия «допуск мастера к изделию».

#### amoCRM

amoCRM — CRM-система, специализирующаяся на управлении воронкой продаж. Имеет удобный интерфейс и развитую экосистему интеграций. Стоимость — от 599 рублей в месяц за пользователя [4].

Система хорошо подходит для контроля коммерческой стадии (переговоры с клиентом, согласование условий), но полностью лишена инструментов для управления производственным процессом. Каталог продукции отсутствует как понятие.

#### Trello

Trello — веб-сервис для управления проектами методом канбан-досок. Интуитивно понятный интерфейс, низкий порог входа, бесплатный тариф покрывает базовые нужды [5].

Мастерская теоретически могла бы использовать Trello для отслеживания производственных задач. Однако связи между карточками (задача привязана к конкретному изделию, которое является частью заказа, который принадлежит клиенту) в Trello невозможно выразить нативно. Каталога нет. Управление специализациями мастеров не поддерживается.

#### Jira

Jira — система управления задачами и проектами компании Atlassian, ориентированная на разработку программного обеспечения. Предоставляет расширенные возможности настройки рабочих процессов, отчётности и интеграций [6]. Стоимость — от 8,15 долларов США за пользователя в месяц.

Для мастерской Jira является избыточным инструментом: сложный и насыщенный интерфейс потребует длительного обучения персонала, не имеющего технического образования. Встроенного каталога продукции нет. Концепция «допуска» не реализована.

#### Craft CMS

Craft CMS — гибкая система управления контентом, обеспечивающая полный контроль над структурой данных и внешним видом [7]. Позволяет создать полностью кастомизированный каталог с любым дизайном.

Craft CMS подошла бы для создания публичного каталога с тематическим оформлением, однако является лишь CMS и не содержит никаких инструментов управления производством. Совместное использование Craft CMS для каталога и другой системы для производства означало бы дублирование данных о товарах в двух местах.

### 1.2.3 Нефункциональные требования

**Производительность.** Первоначальная загрузка каталога (эндпоинт /api/bootstrap/) должна завершаться не более чем за 2 секунды при базе до 500 товаров на сервере с 1 CPU и 2 ГБ RAM. Интерфейс должен оставаться отзывчивым при применении фильтров без обращения к серверу (фильтрация на стороне клиента).

**Безопасность.** Аутентификация реализуется на основе серверных сессий Django с httpOnly cookie. Все небезопасные HTTP-методы (POST, PATCH, DELETE) требуют корректного CSRF-токена. Производственная панель недоступна без авторизации. Конфигурационные секреты (ключи API, пароли) хранятся исключительно в переменных окружения, не в репозитории.

**Надёжность.** Потеря соединения с сервером не должна приводить к потере введённых данных. При недоступности внешних сервисов (ВКонтакте, Telegram) система продолжает функционировать корректно — интеграционные операции выполняются по возможности и не блокируют основной процесс.

**Адаптивность.** Публичная часть корректно отображается на экранах шириной от 375 пикселей (мобильный телефон) до 2560 пикселей (широкоформатный монитор). Производственная панель оптимизирована для настольных экранов, но остаётся работоспособной на планшетах.

**Совместимость.** Поддерживаются актуальные версии браузеров: Chrome 110+, Firefox 110+, Safari 16+, Edge 110+. Для функционирования не требуется установка каких-либо расширений или плагинов.

**Сопровождаемость.** Код покрыт автоматическими тестами не менее чем на 80% по строкам для критических модулей. Все конфигурационные параметры описаны в файле .env.example с комментариями.

**Доступность.** Сайт должен быть доступен не менее 99,5% времени (не более 44 часов простоя в год). Для этого обеспечивается автоматический перезапуск Gunicorn через systemd при аварийном завершении.

При проектировании системы приняты следующие ограничения и допущения:

## 1.3 Проектирование

### 1.3.1 Логическое обоснование и описание структуры и алгоритмов функционирования программы

#### 1.3.1.1 Выбор архитектурного паттерна

На этапе проектирования рассматривались три подхода к организации веб-приложения: традиционное серверное рендеринг (SSR, Server-Side Rendering), многостраничное приложение с динамическими элементами (MPA + AJAX) и одностраничное приложение (SPA) с отдельным REST API.

Подход SSR предполагает, что сервер при каждом запросе формирует готовую HTML-страницу. Достоинства — хорошая индексируемость поисковыми роботами и быстрое отображение первого экрана. Недостатки применительно к данному проекту — высокая нагрузка на сервер при работе производственной панели, где частые обновления данных потребовали бы постоянной перезагрузки страниц.

Подход MPA + AJAX улучшает отзывчивость интерфейса, сохраняя серверный рендеринг для начальной загрузки. Однако при реализации сложных интерактивных компонентов (канбан-доска, матрица допусков, лайтбокс галереи) этот подход быстро усложняется и превращается в де-факто SPA на уровне отдельных страниц.

Подход SPA + REST API выбран как оптимальный по следующим основаниям:

1) Чёткое разделение ответственности: бэкенд отвечает исключительно за данные и бизнес-логику, фронтенд — за представление. Это позволяет разрабатывать и тестировать их независимо;
2) Интерфейс остаётся отзывчивым при навигации: переход между каталогом, карточкой товара и производственной панелью происходит без перезагрузки страницы;
3) REST API, разработанный для фронтенда, автоматически становится интерфейсом для возможных будущих клиентов — мобильного приложения, сторонних интеграций;
4) SEO-индексируемость для данного проекта менее критична: клиенты приходят преимущественно из группы ВКонтакте, а не через поисковые системы.

#### 1.3.1.2 Общая архитектура системы

Система построена по классической трёхзвенной клиент-серверной архитектуре с дополнительным уровнем обратного прокси.

[Рисунок 2 — Архитектурная схема системы (C4 Level 2)]

Описание уровней системы:

**Клиентский уровень.** React SPA, собранный инструментом Vite в набор статических файлов (HTML, JavaScript, CSS). При первом обращении браузер получает index.html и JavaScript-бандл; в дальнейшем все взаимодействия с сервером выполняются через fetch-запросы к REST API. Состояние приложения хранится в памяти браузера (React-состояние корневого компонента App).

**Уровень обратного прокси (Nginx).** Принимает все входящие HTTP-соединения на порту 8080. Для URL-путей, начинающихся с /api/ или /admin/, проксирует запросы на Gunicorn через UNIX-сокет. Для остальных путей возвращает статические файлы из директории dist/ (собранный фронтенд); для любого неизвестного пути возвращает index.html, обеспечивая SPA-роутинг.

**Уровень приложения (Gunicorn + Django).** Gunicorn — WSGI-сервер, который запускает несколько рабочих процессов Django. Django обрабатывает запросы, применяет бизнес-логику, взаимодействует с базой данных через ORM и возвращает JSON-ответы.

**Уровень данных.** SQLite — встроенная в Python база данных без отдельного процесса. Файл базы хранится на диске сервера в директории проекта. Для продакшн-развёртывания с высокой нагрузкой возможна миграция на PostgreSQL без изменений в коде (только настройки Django).

#### 1.3.1.3 Алгоритм инициализации приложения

При открытии сайта браузер загружает статические файлы фронтенда, после чего React-приложение выполняет три параллельных HTTP-запроса:

1) GET /api/csrf/ — получение CSRF-cookie. Django устанавливает cookie csrftoken, которая в дальнейшем используется для всех небезопасных запросов;
2) GET /api/bootstrap/ — основной запрос инициализации. Возвращает в одном ответе: массив всех товаров (до 1000 позиций), массив отзывов, объект с внешними ссылками (ВКонтакте, Telegram). Этот подход устраняет необходимость нескольких последовательных запросов и ускоряет первый рендер каталога;
3) GET /api/auth/me/ — проверка текущей сессии. Если пользователь уже был авторизован (cookie sessionid сохранился с предыдущего сеанса), возвращает данные пользователя; в противном случае возвращает 401, и кнопка «Войти» остаётся видимой.

После получения ответа от /api/bootstrap/ каталог отображается немедленно. Фильтрация, поиск и сортировка выполняются на стороне клиента через useMemo, без дополнительных запросов к серверу.

#### 1.3.1.4 Алгоритм создания заказа и автоматической генерации задач

Создание заказа — ключевой производственный сценарий системы. Алгоритм реализован в представлении WorkshopOrderCreateView и вспомогательной функции _create_tasks_for_order:

1) Руководитель заполняет форму заказа: выбирает или создаёт клиента, указывает тип заказа (предмет/комплект/услуга), выбирает конкретное изделие или комплект, задаёт дедлайн, при необходимости — сумму и аванс;
2) Если сумма не указана явно, она берётся из поля price_from изделия или комплекта; аванс по умолчанию устанавливается в 50% от суммы;
3) В БД создаётся запись Order с начальным статусом new;
4) Вызывается _create_tasks_for_order(order). Функция анализирует тип заказа:
   - Если тип «предмет» — создаётся одна задача Task с product=изделие, status=pending;
   - Если тип «комплект» — для каждого изделия в составе комплекта создаётся отдельная задача Task;
   - Если тип «услуга» — создаётся одна задача с product=None и product_name из поля конфигурации;
5) Созданные задачи автоматически становятся видимыми в стеке тем мастерам, у которых есть допуск к соответствующему изделию.

[Рисунок 3 — Диаграмма деятельности: алгоритм создания заказа и задач]

Такая схема обеспечивает автоматический маршрутинг работ без ручного назначения: руководитель создаёт заказ, задачи попадают в общий пул, из которого мастера самостоятельно берут работу в соответствии со своими допусками.

#### 1.3.1.5 Алгоритм системы допусков мастеров

Матрица допусков реализуется через модель MasterApproval, каждая запись которой связывает одного мастера (ссылка на User) с одним изделием (ссылка на Product). Уникальное ограничение по паре (master, product) исключает дублирование.

При запросе стека задач (GET /api/workshop/tasks/?view=stack) система:
1) Получает список product_id из таблицы MasterApproval, отфильтрованный по текущему пользователю;
2) Возвращает только те задачи, у которых product_id входит в этот список;
3) Дополнительно фильтрует задачи по статусу pending (только те, которые никем не взяты).

Суперадмин (is_superuser) получает все задачи вне зависимости от допусков, что позволяет руководителю контролировать весь производственный стек.

Жизненный цикл задачи имеет три статуса: pending → taken → done. Обратный переход (taken → pending) возможен при освобождении задачи мастером. Переход done → pending не предусмотрен; если работа должна быть переделана, создаётся новая задача.

[Рисунок 4 — Диаграмма состояний задачи]

#### 1.3.1.6 Алгоритм репоста ВКонтакте → Telegram

Интеграция реализует автоматическую пересылку публикаций группы ВКонтакте в Telegram-канал. Алгоритм:

1) В настройках группы ВКонтакте (раздел «Работа с API» → «Callback API») настраивается сервер с URL /api/integrations/vk/callback/ и секретным ключом;
2) При публикации нового поста ВКонтакте отправляет POST-запрос на указанный URL;
3) Обработчик VkCallbackView проверяет секретный ключ в теле запроса. Несовпадение ключа — ответ 403, обработка прерывается;
4) Проверяется тип события: если type ≠ wall_post_new, возвращается «ok» без обработки;
5) Если поле copy_history присутствует в объекте поста — это репост чужой записи; пропускается;
6) Если post_type = «postpone» — запись ещё не опубликована фактически; пропускается;
7) Дедупликация: проверяется кэш Django по ключу vk_post_{owner_id}_{post_id} с TTL 24 часа. Если ключ присутствует — дубль, пропускается. Иначе ключ устанавливается;
8) Пост сохраняется в модель VKPost (для отображения в блоке новостей на сайте);
9) Функция parse_post() извлекает текст и фотографии. Текст очищается от VK-тегов (упоминания вида [id123|Имя] преобразуются в «Имя»), к тексту добавляется постоянная ссылка на запись. Текст усекается до лимита Telegram (1024 символа для подписи к фото, 4096 для текстового сообщения);
10) Функция repost_to_channel() отправляет пост в Telegram: одно фото — sendPhoto с подписью; несколько фото — sendMediaGroup (альбом до 10 фото); только текст — sendMessage;
11) Telegram-бот отвечает 200 OK. ВКонтакте получает ответ «ok» в любом случае — ошибки в интеграции с Telegram не влияют на обработку события ВКонтакте.

#### 1.3.2.2 Взаимодействие с ВКонтакте

Взаимодействие с платформой ВКонтакте организовано через Callback API — механизм, при котором платформа активно уведомляет приложение о событиях, отправляя POST-запросы. Это исключает необходимость периодических опросов (polling) со стороны приложения.

Для активации Callback API в настройках сообщества ВКонтакте выполняется одноразовая процедура подтверждения: ВКонтакте отправляет запрос с типом confirmation на настроенный URL; сервер возвращает строку подтверждения (VK_CONFIRMATION_TOKEN), доказывая, что данный URL принадлежит администратору сообщества.

Получаемые события: wall_post_new (новая запись на стене). Сервер подписывается именно на этот тип событий в настройках Callback API.

Дополнительный канал взаимодействия с ВКонтакте — RSS-лента группы (https://vk.com/rss/wall-{owner_id}.rss). Этот механизм используется в эндпоинте /api/vk-posts/ для получения актуальных публикаций без API-ключа, только по открытому идентификатору сообщества.

#### 1.3.2.3 Взаимодействие с Telegram

Отправка сообщений в Telegram реализуется через Telegram Bot API. Приложение выступает в роли активного клиента (не вебхук-получателя): при получении события от ВКонтакте сервер сам инициирует HTTP-запрос к API Telegram.

Используемые методы Bot API:
- sendMessage — отправка текстового сообщения в канал (параметры: chat_id, text);
- sendPhoto — отправка одной фотографии с подписью (параметры: chat_id, photo, caption);
- sendMediaGroup — отправка группы фотографий (альбом) с подписью на первом элементе (параметры: chat_id, media — массив объектов InputMedia).

Выбор метода осуществляется автоматически функцией repost_to_channel() в зависимости от наличия и количества фотографий в исходном посте. Все три метода задействуют единый токен Telegram-бота, настроенный в переменной окружения TELEGRAM_BOT_TOKEN.

#### 1.3.2.4 Взаимодействие с SMTP-сервером

Email-уведомления о приближающихся дедлайнах отправляются через Django-модуль django.core.mail. Параметры SMTP-подключения (хост, порт, логин, пароль) передаются через переменные окружения. Поддерживаются как SSL-соединение (порт 465), так и TLS через STARTTLS (порт 587).

Management-команда notify_urgent_orders запускается планировщиком cron раз в сутки в 09:00. Она находит все активные заказы (статус new или in_progress) с дедлайном через 14, 7 или 3 дня от текущей даты и отправляет письма ответственному мастеру и администратору.

#### 1.3.3.2 Входные данные системы

Система принимает входные данные из трёх источников.

**HTTP-запросы от браузера.** Тело запроса передаётся в формате JSON (Content-Type: application/json). Параметры фильтрации и пагинации передаются в строке запроса (query string). Файлы (изображения) в данной версии системы не загружаются через API — используются ссылки на внешние URL.

**Вебхук-событие от ВКонтакте.** POST-запрос на /api/integrations/vk/callback/ с телом в формате JSON по спецификации VK Callback API. Ключевые поля события wall_post_new: type (тип события), object.id (ID поста), object.owner_id (ID сообщества), object.text (текст записи), object.attachments (вложения: фотографии, ссылки), object.date (Unix timestamp публикации), secret (секретный ключ).

**Вебхук-событие от Telegram.** POST-запрос на /api/integrations/telegram/webhook/ с телом по спецификации Telegram Bot API (объект Update). В текущей версии принимается и подтверждается, но содержательная обработка не реализована (заглушка для будущего расширения).

#### 1.3.3.3 Выходные данные системы

**Ответы REST API** возвращаются в формате JSON с кодом состояния HTTP, соответствующим результату операции (200 OK, 201 Created, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found).

Ответ /api/bootstrap/ содержит:
- products — массив объектов Product, сериализованных в camelCase (priceFrom, leadTime, protectionClass). Поле setDiscounts содержит список комплектов, в которые входит товар, с процентом скидки;
- reviews — массив объектов Review;
- links — объект с ключами vkCommunity, vkMessages, telegramPublic;
- total, page, hasNext — метаданные пагинации.

**Ответ на вебхук ВКонтакте** — строка «ok» с Content-Type: text/plain. Требование задокументировано в документации ВКонтакте Callback API: любой ответ, отличный от «ok», интерпретируется как ошибка, и ВКонтакте повторяет попытку отправки.

**Статические файлы** (HTML, CSS, JavaScript, изображения) раздаются Nginx из директории dist/ при запросах к публичной части сайта.

#### 1.3.3.4 Сериализация данных

DRF-сериализаторы преобразуют объекты Django-моделей в JSON и обратно. В ProductSerializer применено ручное сопоставление полей: snake_case-поля модели (price_from, lead_time, protection_class) преобразуются в camelCase (priceFrom, leadTime, protectionClass) для удобства использования в JavaScript/TypeScript-коде фронтенда.

Вычисляемое поле setDiscounts не хранится в базе данных: оно вычисляется в момент сериализации через SerializerMethodField. Для каждого товара выполняется запрос к ProductSet, отфильтрованный по включению данного товара, и вычисляется процент скидки как (1 — price_from_комплекта / sum(price_from_товаров)) × 100.

Для оптимизации производительности все связанные объекты загружаются в один запрос через prefetch_related. Без этой оптимизации при 200 товарах в каталоге возникла бы проблема N+1 запросов.

## 2.1 Программная реализация

### 2.1.1 Технические средства реализации

#### 2.1.1.1 Серверная часть

Серверная часть системы реализована на языке **Python 3.11** с использованием веб-фреймворка **Django 5.2**.

Django выбран по нескольким ключевым соображениям. Во-первых, фреймворк предоставляет встроенную систему аутентификации и управления сессиями, которая удовлетворяет всем требованиям безопасности без необходимости реализовывать её самостоятельно. Во-вторых, механизм миграций базы данных обеспечивает управляемую эволюцию схемы при итеративной разработке. В-третьих, встроенная панель администратора Django (/admin/) предоставляет резервный интерфейс управления данными без дополнительных усилий. Версия 5.2 выбрана как актуальная LTS-версия на момент начала разработки, гарантирующая поддержку до 2028 года.

Для построения REST API использован **Django REST Framework 3.16** (DRF). Он предоставляет базовые классы APIView с автоматической сериализацией/десериализацией JSON, встроенным CSRF-контролем и механизмом разрешений. Архитектура «представление на основе классов» (class-based views) позволила вынести общую логику проверки аутентификации в базовый класс и переопределять её только там, где это необходимо (публичные эндпоинты, webhook-приёмники).

Для раздачи статических файлов применена библиотека **WhiteNoise 6.9** с расширением Brotli. WhiteNoise интегрируется в цепочку WSGI-middleware и позволяет Django самостоятельно обслуживать статические файлы с высоким уровнем производительности: файлы кешируются в памяти при старте, заголовки Cache-Control устанавливаются автоматически, компрессия Brotli снижает объём передаваемых данных на 15–25% по сравнению с gzip.

Настройка доступа с фронтенда (другой порт в режиме разработки) обеспечена библиотекой **django-cors-headers 4.7**. CORS-заголовки добавляются только для перечисленных в настройках доменов, что исключает несанкционированные кросс-доменные запросы.

Для планирования фоновых задач — в частности, email-уведомлений о приближающихся дедлайнах — применена библиотека **python-crontab 3.3**, позволяющая программно управлять crontab-записями текущего пользователя из кода Django-команды управления.

HTTP-запросы к внешним API (ВКонтакте, Telegram) выполняются через библиотеку **requests 2.32**.

Производственный WSGI-сервер — **Gunicorn**, запускающий три рабочих процесса. Gunicorn принимает соединения через UNIX-сокет `/run/calradia/calradia.sock`, что обеспечивает более низкую латентность по сравнению с TCP-соединениями на localhost и исключает лишние сетевые затраты.

Управление жизненным циклом сервиса осуществляется через **systemd**. Unit-файл calradia.service задаёт параметры RuntimeDirectory (автоматическое создание директории сокета при старте), EnvironmentFile (загрузка секретов из .env) и перезапуск при сбое (Restart=on-failure). Это обеспечивает требование доступности системы не менее 99,5%.

В качестве **СУБД** используется SQLite 3. Файл базы данных хранится в корневой директории проекта. Выбор SQLite обоснован малым объёмом данных (менее 1000 изделий, менее 50 одновременных заказов) и отсутствием необходимости в параллельных операциях записи. SQLite не требует отдельного серверного процесса, что упрощает развёртывание на одном VPS.

Обратный прокси-сервер **Nginx** принимает запросы на порту 8080 и распределяет их: запросы к `/api/*` и `/admin/*` передаются Gunicorn через UNIX-сокет, остальные — обслуживаются из директории с собранным фронтендом. Конфигурация `try_files $uri $uri/ /index.html` обеспечивает SPA-роутинг: обновление страницы на любом URL возвращает index.html, после чего маршрутизация выполняется React Router на стороне клиента.

#### 2.1.1.2 Клиентская часть

Клиентская часть разработана как одностраничное приложение (SPA) на языке **TypeScript 5.x** с использованием библиотеки **React 19**.

React 19 выбран в первую очередь ради компонентной модели, позволяющей разбить сложный интерфейс (каталог с фильтрами, канбан-доска, матрица допусков, галерея с лайтбоксом) на независимые переиспользуемые компоненты. Хуки состояния и эффектов (useState, useEffect, useMemo) обеспечивают реактивный интерфейс без дополнительных библиотек управления состоянием — объём данных приложения достаточно мал, чтобы хранить их в родительском компоненте App и передавать через props.

TypeScript обеспечивает статическую типизацию: все доменные сущности (Product, Order, Task, Client, MasterApproval и другие) описаны в файле types.ts, что позволяет компилятору обнаруживать несоответствия типов на этапе разработки.

Сборщик **Vite 6** обеспечивает быстрый цикл разработки (HMR — горячая замена модулей) и оптимизированную финальную сборку (разбиение на чанки, tree-shaking, минификация). Время первоначальной сборки не превышает 15 секунд на машине разработчика.

Для иконографии применена библиотека **Lucide React** — набор из более 1000 SVG-иконок с консистентным визуальным стилем, поставляемых как React-компоненты и включаемых только в той части, что используется в коде (tree-shakeable).

Сторонние CSS-фреймворки не используются: все стили написаны вручную в файле styles.css с использованием CSS-переменных (custom properties) для цветовой палитры и интервалов. Это обеспечивает полный контроль над визуальным стилем в соответствии с тематикой средневековой кузницы.

Для автоматического тестирования фронтенда применён фреймворк **Vitest** совместно с **@testing-library/react**. Vitest интегрируется с Vite и позволяет использовать ту же конфигурацию TypeScript, что и в основном коде приложения. Покрытие кода измеряется через **@vitest/coverage-v8**.

#### 2.1.1.3 Инфраструктура и окружение разработки

Развёртывание производится на VPS под управлением **Debian 11** с 2 ГБ оперативной памяти и 1 vCPU. Такая конфигурация типична для малого бизнеса и соответствует требованиям нефункциональной спецификации.

Управление зависимостями серверной части осуществляется через стандартный файл `requirements.txt`. Для изоляции зависимостей применяется виртуальное окружение Python (venv). Зависимости клиентской части управляются через **npm** и зафиксированы в `package-lock.json`.

Конфигурационные секреты (SECRET_KEY, ключи VK и Telegram, SMTP-реквизиты) хранятся в файле `.env` на сервере и загружаются в окружение процесса Django через директиву `EnvironmentFile` systemd-юнита. Файл `.env.example` с описанием всех параметров включён в репозиторий.

Система контроля версий — **Git**, удалённый репозиторий размещён на GitHub. Ветвление организовано по модели feature-branches.

### 2.1.2 Описание разработанных алгоритмов

#### 2.1.2.1 Алгоритм начальной загрузки данных (bootstrap)

Производительность первого рендера каталога является критическим показателем пользовательского опыта. Если бы фронтенд загружал товары, отзывы и ссылки тремя отдельными запросами, задержка вырастала бы втрое из-за последовательного выполнения fetch-вызовов (каждый последующий ожидает предыдущего).

Эндпоинт `/api/bootstrap/` решает эту проблему, объединяя все необходимые данные в одном ответе. Алгоритм работы представления BootstrapView:

1. Формируется QuerySet товаров с предварительной загрузкой (prefetch_related) связанных фотографий галереи и комплектов. Это исключает проблему N+1 запросов: вместо одного SQL-запроса на каждый из N товаров выполняется один общий запрос на все фотографии.
2. Все товары сериализуются в JSON-массив. Клиент получает полный каталог и хранит его в памяти; вся последующая фильтрация и поиск выполняются клиентским кодом через useMemo без обращения к серверу.
3. Запрашиваются последние 10 опубликованных отзывов — объём достаточный для отображения на странице отзывов.
4. Из таблицы IntegrationLink извлекаются внешние ссылки (ВКонтакте, Telegram, электронная почта). Если записи в базе отсутствуют, используются значения из settings.py.
5. Все три объекта объединяются в один словарь и возвращаются с кодом HTTP 200.

Эндпоинт открыт для анонимного доступа (permission_classes не заданы), поскольку содержит только публичные данные.

#### 2.1.2.2 Алгоритм создания заказа и автоматической генерации задач

Приём нового заказа — наиболее сложный бизнес-сценарий системы. Представление WorkshopOrderCreateView реализует транзакционный алгоритм, состоящий из четырёх фаз:

**Фаза 1. Валидация входных данных.** Из тела запроса извлекаются: имя клиента (обязательное поле), тип заказа (Одиночный/Комплект), список идентификаторов товаров, дата дедлайна (строка ISO 8601), общая сумма и аванс (числа). Отсутствие обязательного поля возвращает HTTP 400 с описанием ошибки.

**Фаза 2. Создание или поиск клиента.** По имени ищется существующий клиент (поиск без учёта регистра). Если клиент не найден — создаётся новая запись. Это позволяет руководителю быстро оформлять повторные заказы, вводя только имя.

**Фаза 3. Создание заказа.** Запись Order сохраняется в базе с начальным статусом «Новый» (new), привязкой к клиенту, датой дедлайна и финансовыми параметрами. К заказу привязываются выбранные товары через отношение ManyToMany.

**Фаза 4. Автоматическая генерация задач.** Вызывается вспомогательная функция `_create_tasks_for_order(order)`. Алгоритм функции:
- Для каждого товара из состава заказа определяется его категория (category): helmet, armour, chainmail, leather, bracers и другие.
- Категория маппируется на направление специализации (Direction) через словарь соответствия: например, категория chainmail → направление chain_mail; категория leather → направление leather.
- По каждому направлению создаётся одна запись Task со статусом «В стеке» (stack), привязкой к заказу и текстовым описанием на основе названия товара.
- Дубликаты задач одного направления в рамках одного заказа не создаются: если заказ содержит несколько кольчужных элементов, создаётся одна задача для мастера по кольчуге.

После сохранения всех задач метод `_sync_order_status(order)` пересчитывает статус заказа в зависимости от статусов задач: если все задачи выполнены — заказ переходит в «Готов»; если хотя бы одна в работе — «В производстве»; если ни одна не взята — «Новый».

#### 2.1.2.3 Алгоритм проверки допуска мастера

Матрица допусков определяет, к задачам каких направлений имеет доступ конкретный мастер. Алгоритм реализован в методе PATCH представления WorkshopTaskDetailView и включает следующие проверки:

1. **Проверка авторизации.** Неавторизованный запрос немедленно отклоняется (HTTP 401).
2. **Получение задачи.** Задача ищется по идентификатору. Если не найдена — HTTP 404.
3. **Ветвление по действию.** В зависимости от переданного поля action выполняется одна из трёх ветвей: take (взять в работу), release (вернуть в стек), done (отметить выполненной).
4. **Проверка допуска при взятии задачи.** Для пользователей без флага is_superuser выполняется дополнительная проверка: существует ли запись MasterApproval с сочетанием (мастер = текущий пользователь, направление = направление задачи). Если запись отсутствует — HTTP 403 с сообщением «Нет допуска к задачам этого направления».
5. **Проверка статуса задачи.** Задачу можно взять только из состояния «В стеке»; вернуть или отметить выполненной — только из состояния «В работе». Нарушение — HTTP 400.
6. **Проверка «чужой задачи».** Вернуть задачу или отметить её выполненной может только тот мастер, который её взял, либо администратор. Иначе — HTTP 403.

Суперпользователь проходит проверки с пункта 4 по 6 в упрощённом режиме: допуск не требуется, «чужая задача» не является ограничением.

Аналогичная логика применяется к стеку задач, видимому мастеру в WorkshopTasksView: запрос к GET /api/workshop/tasks/ для мастера (не суперпользователя) возвращает только задачи со статусом «В стеке» по направлениям, на которые у него есть допуск, плюс задачи, уже взятые им самим.

#### 2.1.2.4 Алгоритм репоста публикации ВКонтакте в Telegram

Интеграция ВКонтакте → Telegram реализована по событийной модели: ВКонтакте отправляет HTTP-запрос на сервер при каждом новом событии в группе.

**Шаг 1. Получение события.** Nginx проксирует POST-запрос на `/api/vk/callback/` к представлению VkCallbackView. Представление проверяет HMAC-подпись запроса (поле secret должно совпадать с токеном из settings.py). Запросы с неверной подписью отклоняются (HTTP 403).

**Шаг 2. Обработка подтверждения.** При первой настройке Callback API ВКонтакте отправляет событие с type=confirmation. Представление возвращает строку подтверждения в формате plaintext — это необходимо для верификации адреса callback.

**Шаг 3. Парсинг поста.** При получении события типа wall_post_new вызывается функция `parse_post(post_data)` из модуля services/vk.py. Функция:
- Извлекает текст поста, обрезает упоминания (@club...) через регулярное выражение.
- Ограничивает длину текста 1000 символами.
- Собирает список URL фотографий: для каждого вложения типа photo выбирается версия с наибольшим разрешением.
- Фильтрует рекламные посты (наличие поля marked_as_ads == 1).

**Шаг 4. Проверка дедупликации.** По идентификатору поста ВКонтакте (vk_id) проверяется наличие записи в таблице VKPost. Если запись существует — пост уже был переслан, обработка завершается. Иначе запись создаётся.

**Шаг 5. Отправка в Telegram.** Вызывается функция `repost_to_telegram(text, photos)` из модуля services/telegram.py. Если список фотографий пуст — отправляется простое текстовое сообщение (sendMessage). При наличии одной фотографии — sendPhoto с подписью. При наличии нескольких — sendMediaGroup (альбом).

**Шаг 6. Обработка ошибок.** Если Telegram API недоступен (сеть, превышение лимита запросов), исключение перехватывается, в лог записывается предупреждение, а в ВКонтакте всё равно возвращается HTTP 200 с телом `ok`. Это обязательно: если Callback API ВКонтакте получает ошибку, он повторяет запрос несколько раз, что приведёт к дублированию постов.

#### 2.1.2.5 Алгоритм email-уведомлений о дедлайнах

Уведомления отправляются управляющей командой Django `notify_urgent_orders`. Алгоритм:

1. Запрашиваются все заказы в статусах «Новый», «В производстве» и «Готов» (кроме «Отменён» и «Выдан»).
2. Для каждого заказа вычисляется количество дней до дедлайна: `days_left = (deadline - today).days`.
3. Если days_left равно 14, 7 или 3 — формируется email-уведомление руководителю с именем клиента, описанием заказа и датой дедлайна.
4. При наличии флага `--dry-run` команда только выводит список заказов, которые попали бы в рассылку, без фактической отправки.
5. Команда добавляется в crontab операционной системы: задание выполняется ежедневно в 09:00 по серверному времени.

#### 2.1.2.6 Клиентская фильтрация каталога

Каталог, полученный от `/api/bootstrap/`, хранится в состоянии React-компонента App. Параметры активных фильтров (категория, период, материал, размер, статус наличия, строка поиска, порядок сортировки) также хранятся в состоянии App.

Вычисление отфильтрованного массива товаров для отображения реализовано через хук `useMemo`, зависящий от массива товаров и текущих параметров фильтрации. При изменении любого параметра хук пересчитывается без обращения к серверу.

Алгоритм фильтрации применяет условия последовательно: сначала фильтр по категории, затем по периоду, материалу, размеру, статусу. Строка поиска сопоставляется с полями name и subtitle через `toLowerCase().includes()`. Сортировка применяется в последнюю очередь через `Array.prototype.sort()` с компаратором, соответствующим выбранному критерию (по умолчанию, по дате добавления, по популярности, по сроку изготовления).

## 2.2 Тестирование программного обеспечения

### 2.2.1 Стратегия тестирования

Тестирование системы охватывает два уровня: модульное (unit) тестирование изолированных функций и интеграционное тестирование эндпоинтов API совместно с базой данных.

Для серверной части применён фреймворк Django TestCase, предоставляющий встроенный тестовый клиент (Client) и механизм транзакционной изоляции: каждый тест выполняется в отдельной транзакции, откатываемой после завершения, что исключает влияние одного теста на другие. Для мокирования внешних HTTP-вызовов (Telegram API, ВКонтакте) используется стандартная библиотека unittest.mock.

Для клиентской части применён фреймворк Vitest совместно с @testing-library/react. Тесты рендерят компоненты в виртуальном DOM (jsdom) и проверяют наличие ожидаемых элементов через запросы по тексту, роли и атрибутам, соответствующие реальному использованию компонента.

Выполнение всех тестов автоматизировано: серверные тесты запускаются командой `python manage.py test`, клиентские — командой `npm test`.

### 2.2.2 Модульные тесты

Модульные тесты расположены в файле `workshop/tests/test_unit.py`. Тестируются изолированные функции без обращения к базе данных и внешним сервисам.

**Модуль services/telegram.py.** Тестируются четыре сценария:
- Функция `get_api_base()` выбрасывает ValueError при отсутствии токена бота в настройках.
- Функция `get_api_base()` возвращает корректный URL при наличии токена.
- Функция `send_message()` выполняет POST-запрос с ожидаемым JSON-телом (имитация через `unittest.mock.patch`).
- Функция `store_update()` возвращает None для неподдерживаемых типов событий Telegram (несобственные сообщения, команды).

**Модуль services/vk.py.** Тестируются пять сценариев парсинга поста:
- Пост без вложений: извлекается только текст, список фото пуст.
- Пост с фотографиями: URL фотографий извлекаются корректно, выбирается максимальное разрешение.
- Пост с упоминаниями (@club...): упоминания удаляются из текста.
- Длинный текст (> 1000 символов): текст обрезается, добавляется многоточие.
- Подпись к альбому (текст при наличии фото): аналогичное обрезание.

**Сериализаторы.** Тестируется корректность отображения полей из snake_case (Python) в camelCase (JSON) для ProductSerializer и ReviewSerializer. Проверяется наличие обязательных полей badge и gallery в ответе.

**Вспомогательные функции views.py.** Тестируется функция `_product_kwargs()`: корректное маппирование входящих camelCase-ключей JSON в snake_case-поля модели; игнорирование неизвестных ключей (защита от перезаписи произвольных полей). Тестируется функция `_unique_slug()`: строчные буквы, длина не более 50 символов, уникальность при повторных вызовах.

### 2.2.3 Интеграционные тесты

Интеграционные тесты расположены в файле `workshop/tests/test_integration.py`. Каждый тестовый класс охватывает один модуль функциональности и проверяет взаимодействие представлений, сериализаторов и базы данных.

**BootstrapIntegrationTests.** Три сценария:
- GET /api/bootstrap/ возвращает HTTP 200 с объектом, содержащим поля products, reviews и links.
- Поле links содержит ожидаемые ключи (vk, telegram, email).
- При наличии записи IntegrationLink в базе её значение используется вместо дефолта из settings.

**ReviewIntegrationTests.** Два сценария:
- POST /api/products/{id}/reviews/ создаёт отзыв и возвращает HTTP 201.
- Запрос к несуществующему товару возвращает HTTP 404.

**ProductCRUDIntegrationTests.** Восемь сценариев:
- Анонимный GET /api/products/ возвращает HTTP 200.
- POST требует авторизации (HTTP 403 для анонима).
- Авторизованный POST создаёт товар, возвращает HTTP 201.
- PATCH обновляет поле товара.
- DELETE удаляет товар.
- PATCH без авторизации возвращает HTTP 403.
- GET /api/products/{id}/ для несуществующего ID возвращает HTTP 404.

**AuthIntegrationTests.** Пять сценариев:

- После входа GET /api/auth/me/ возвращает данные пользователя.

**VkCallbackIntegrationTests.** Четыре сценария:

**TaskApprovalIntegrationTests.** Девять сценариев — наиболее полно покрытый модуль:

- Мастер может отметить свою задачу выполненной.
- Неавторизованный пользователь не может взять задачу (HTTP 401).

- Не-суперпользователь не может управлять допусками (HTTP 403).

**WorkshopOrderIntegrationTests.** Шесть сценариев:
- Неавторизованный пользователь не может просматривать заказы.

**ProductSetCatalogIntegrationTests.** Пять сценариев:
- Список комплектов публично доступен (HTTP 200).

**NotifyUrgentOrdersCommandTests.** Два сценария:

```python
            if ps.price_from:
                discount_pct = (

                          / price_individual * 100)
                    if price_individual else 0
                )

                discount_pct = 0
```

```python
def _sync_order_status(order: Order):
    tasks    = list(order.tasks.all())
    if not tasks:
        return
    all_done  = all(t.status == Task.Status.DONE  for t in tasks)
    any_taken = any(t.status == Task.Status.TAKEN  for t in tasks)
    any_done  = any(t.status == Task.Status.DONE   for t in tasks)

    if all_done:
        new_status = Order.Status.DONE
    elif any_taken or any_done:
        new_status = Order.Status.IN_PROGRESS
    else:
        new_status = Order.Status.NEW

    if (order.status != new_status
            and order.status not in (Order.Status.DONE,
                                     Order.Status.CANCELLED)):
        order.status = new_status
        order.save(update_fields=['status'])
```

```python
class WorkshopTaskDetailView(APIView):
    def patch(self, request, task_id):
        if not _is_staff(request):
            return Response(
                {"detail": "Требуется авторизация."},
                status=status.HTTP_401_UNAUTHORIZED
            )
        task = Task.objects.select_related(
            'order', 'product', 'assigned_to'
        ).filter(pk=task_id).first()
        if not task:
            return Response(
                {"detail": "Задача не найдена."},
                status=status.HTTP_404_NOT_FOUND
            )
        action = request.data.get('action')

        if action == 'take':
            if task.status != Task.Status.PENDING:
                return Response(
                    {"detail": "Задача уже взята."},
                    status=status.HTTP_400_BAD_REQUEST
                )
            if task.product is not None and not request.user.is_superuser:
                approved = MasterApproval.objects.filter(
                    master=request.user, product=task.product
                ).exists()
                if not approved:
                    return Response(
                        {"detail": "Нет допуска к этому предмету."},
                        status=status.HTTP_403_FORBIDDEN
                    )
            task.status      = Task.Status.TAKEN
            task.assigned_to = request.user
            task.save()
            _sync_order_status(task.order)

        elif action == 'done':
            if (task.assigned_to != request.user
                    and not request.user.is_superuser):
                return Response(
                    {"detail": "Нельзя закрыть чужую задачу."},
                    status=status.HTTP_403_FORBIDDEN
                )
            task.status = Task.Status.DONE
            task.save()
            _sync_order_status(task.order)

        elif action == 'release':
            if (task.assigned_to == request.user
                    or request.user.is_superuser):
                task.status      = Task.Status.PENDING
                task.assigned_to = None
                task.save()
                _sync_order_status(task.order)

        else:
            if 'notes' in request.data:
                task.notes = request.data['notes']
                task.save()

        return Response(_task_to_dict(task))
```

```python
import re


def _largest_photo_url(photo: dict) -> str:
    sizes = photo.get("sizes", [])
    if not sizes:
        return ""
    best = max(sizes, key=lambda s: s.get("width", 0) * s.get("height", 0))
    return best.get("url", "")


def _clean_text(text: str) -> str:
    text = re.sub(r'\[(?:id|club|public)\d+\|([^\]]+)\]', r'\1', text)
    text = re.sub(r'\[[^\]]{1,64}\]', '', text)
    return text.strip()


def parse_post(post: dict) -> tuple[str, list[str]]:
    """Вернуть (текст, список URL фотографий) для объекта поста VK."""
    text   = _clean_text(post.get("text", ""))
    photos: list[str] = []

    for att in post.get("attachments", []):
        if att.get("type") == "photo":
            url = _largest_photo_url(att["photo"])
            if url:
                photos.append(url)
        elif att.get("type") == "link":
            link_url = att["link"].get("url", "")
            title    = att["link"].get("title", "")
            if link_url and link_url not in text:
                text = (f"{text}\n"
                        f"{title + ': ' if title else ''}{link_url}").strip()

    owner_id = post.get("owner_id", "")
    post_id  = post.get("id", "")
    if owner_id and post_id:
        vk_url = f"https://vk.com/wall{owner_id}_{post_id}"
        text   = f"{text}\n\n🔗 {vk_url}".strip()

    limit = 1024 if photos else 4096
    if len(text) > limit:
        text = text[: limit - 3] + "..."

    return text, photos
```
